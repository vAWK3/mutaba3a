- MUT-441's server receipt reading is merged and **off** (`server_ocr_enabled = false`): the release only sets `SERVER_OCR=false` on the API, creates nothing and builds no OCR image. Don't turn it on in the current project: the first apply that creates it comes **after MUT-487** moves the stack to its own project (plan D6), or the service, network, queue and accounts would be made in `malafat-production` only to be moved. **To pilot it, in the new project:**
  - Terraform enables `cloudtasks.googleapis.com` and `compute.googleapis.com` itself once the flag is on (no manual step). Enabling Compute may create the project's `default` VPC with its open-ingress rules; nothing runs in it, but delete it (`gcloud compute networks delete default`, after deleting its firewall rules) unless the org policy `compute.skipDefaultNetworkCreation` already prevents it. Check `gcloud tasks locations list` lists `me-west1` before the apply.
  - Set `server_ocr_enabled = true` in `production.tfvars` (git-ignored) **only when piloting**, and release the server (`make release server`): `deploy.sh` then builds and pushes `receipt-ocr:<sha>` from `server/ocr` (about 1.2 GB, minutes) and the apply creates the `receipt-ocr` service (4 vCPU / 4 GiB, min 0 / max 3, startup CPU boost), its network (Direct VPC egress `ALL_TRAFFIC` into `receipt-ocr`, no NAT, no default route, deny-all egress at priority 0), the `receipt-reads` queue (3 in flight), the 5-minute `receipt-read-sweep` job and the three service accounts. Review the plan: only `receipt_ocr.tf` resources, the two APIs and the API's env should change.
  - After the release: `terraform output receipt_ocr_url` is set; `gcloud run services get-iam-policy receipt-ocr` lists only the API's service account; an unauthenticated `curl -s -o /dev/null -w '%{http_code}' -X POST $(terraform output -raw receipt_ocr_url)/v1/read` answers 401 or 403 (IAM refuses it before the sidecar sees it); `gcloud scheduler jobs run receipt-read-sweep --location=me-west1` and the API's log show a `swept` run.
  - Grant `receipt_reading` per pilot user in the operator console (MUT-460); each grant also queues that person's unread To-review receipts (R5). Nobody else's receipts are read.
  - A rollback (`make rollback-server`) pins `receipt-ocr` to the target commit's image, or keeps the running one when that commit has none (F6). To switch reading off, set `server_ocr_enabled = false` and release: the service, queue and job are destroyed and receipts stay unread (`readStatus` untouched). `ocr_min_instances = 1` keeps one warm (about $50–70 a month) if pilots find the first read slow (R4).
  - **Rolling back to an API from before MUT-441** (one with no `/jobs/v1/receipts/read`): first switch reading off, set `server_ocr_enabled = false` and apply, or at least pause the sweep, `gcloud scheduler jobs pause receipt-read-sweep --location=me-west1`. Otherwise the older API answers the 5-minute sweep (and any queued `receipt-reads` task) with 401/404/503 every time, Cloud Tasks retries, and the MUT-328 error alerts fire for nothing. Resume it (`gcloud scheduler jobs resume receipt-read-sweep --location=me-west1`) once an API with MUT-441 is back.
  - Delete this item and record the date on MUT-441.
