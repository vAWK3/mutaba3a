# MUT-236 — Portal: set your password from a setup link

Jira: MUT-236 (Story, epic MUT-34). Blocked by MUT-235 (server half, In Review, branch `feature/mut-235-setup-links`, not merged to main). This branch, `feature/mut-236-setup-page`, is cut from it. Relates: MUT-209 (Arabic default), MUT-111 (app links), ADR-037, ADR-088, TD-149.
Status: plan. Portal only (`src/hosted/**`), plus one server test line, the release-QA catalog and docs.

**Release coupling (eng review A3 of MUT-235):** the portal is served by the same server build, so MUT-235 and MUT-236 ship in one `make release server`. Never cut a server release between the two merges.

## 1. Problem and acceptance criteria

Since MUT-235 a new or reset account gets a one-time link `https://<portal>/setup#<token>` from Basel. The portal has no `/setup` page, so the link lands on the SPA fallback, and without this ticket nobody can finish setting up.

Acceptance criteria (ticket + Jira comment 11759 + TD-149):

1. The page reads the token from the fragment, then removes it from the address bar (`history.replaceState`, through the router) before the person does anything.
2. It checks the link (`POST /v1/account-setup/check`) before showing a form. Expired, used, superseded and invalid links each show their own message, in EN and AR (RTL), and no form.
3. It opens in the account's locale from the check response, unless this browser already holds a language the person chose (MUT-209 rule); before the check answers, and on any refusal, the usual default applies (choice, else last account's hint, else Arabic).
4. Form: the email in a visible read-only `autocomplete="username"` input (D2), and one new-password field with `autocomplete="new-password"`. The 12–128 rule is visible next to the field, and a password outside it is refused inline before any request.
5. On success the page signs in through the existing `POST /v1/sessions` with the returned email and the new password, and lands on Home (`/` → first profile).
6. TD-149: submit is disabled while the request is in flight; a 410 `used` after an earlier attempt that got no answer (timeout, network) first tries the sign-in with the typed password (D3); if that fails it says "your password is probably set, try signing in", not "ask for a new link".
7. `/setup` stays out of `ALLOWED_APPLINKS_PATHS` (it already is; a test pins it by name).
8. The ADR-037 bundle-wording rules (`scripts/bundle-rules.ts` `HOSTED_RULES`) still pass: no "reset password", "invite", "forgot", "sign up", "إعادة تعيين", "دعوة", "نسيت", "إنشاء حساب", "اشترك" in the copy.
9. Release-QA: `qa/features/portal/setup.yaml` + a passing `qa/specs/portal/setup.spec.ts` against stubbed `/v1`.

Check of the comment's bundle-test question: the test exists. `scripts/check-bundles.ts` applies `HOSTED_RULES` to `dist-hosted` in `npm run build`, and `auth-states.test.tsx` has a matching `BANNED` regex. The new copy is written to pass both (§5); the rules themselves don't change.

### 2.2 Flow

```
/setup#<token>
  │ first render: token := tokenFromHash(location.hash)   (kept in component state)
  │ effect: navigate({ to: '/setup', replace: true })      (fragment gone from the bar and history)
  ├─ token null ────────────────────────────────► Refused 'missing'   ("open the whole link again")
  └─ check (useQuery, retry off, 15 s timeout)
       ├─ pending ─► CheckingSession label "Checking your link"
       ├─ network / 5xx ─► Unreachable card + Try again (refetch)
       ├─ 429 ─► rate-limited card (minutes) + Try again
       ├─ 422 (malformed token) ─► Refused 'invalid'
       ├─ { state: expired|used|superseded|invalid } ─► Refused <state>
       └─ { state: valid, email, locale, purpose }
            │ useLayoutEffect: adoptAccountLocale(locale)   (before the form's first paint)
            ▼
          Form ── local policy fails ─► inline field error, nothing sent
            │ submit (disabled while pending)
            ▼
          redeem (15 s timeout)
            ├─ 200 { email } ─► signIn(email, password)
            │     ├─ ok ─► clear cache, set ME, adopt me.user.locale, navigate('/', replace) → Home
            │     └─ fails ─► PasswordSet card: "Your password is saved. Sign in to continue." + link
            ├─ 410 state ─► answerLost && state==='used'
            │                  ? signIn(email, typed password) (D3): ok ─► Home; fails ─► Refused 'usedAfterRetry'
            │                  : Refused <state>
            ├─ 422 ─► inline policy error (server disagreed: shouldn't happen)
            ├─ 429 ─► banner, minutes; form stays
            └─ network / timeout ─► banner "couldn't reach"; answerLost := true; form stays
```

The check query (eng review A1) sets `staleTime: Infinity`, `gcTime: 0`, `retry: false`, `refetchOnWindowFocus: false`, `refetchOnReconnect: false`: the portal default (30 s stale, refetch on focus) would re-check after a trip to the password manager, and once a redeem has run the answer is `used`. The page's state after Save comes from the redeem, never from the check again.

`answerLost` is a ref set when a redeem attempt ended without an HTTP answer; it never resets on this page, so any later `used` reads as "probably set".

### 2.3 Token handling

- Read once, from the router's location (`useLocation().hash`, no `#`), in a lazy `useState` initializer, so StrictMode's double render reads the same value and the stripped URL can't erase it.
- Stripped with `navigate({ to: '/setup', replace: true })` in a mount effect. The browser router implements `replace` with `history.replaceState`, so the token is in no history entry after the first frame; memory history (unit tests) behaves the same, so the strip is testable without a browser.
- The token lives only in React state. No storage (hosted-portal.md §7.1: the language is the only thing the portal stores). Consequence: a reload after the strip has no token → the `missing` message, which says to open the link from the message again. That is the price of AC 1, and it is honest.
- It travels only in the JSON body of the two calls; it is never in a URL, query key, log or error.
- No client-side shape check beyond "non-empty": the server's 422 for a malformed token maps to `invalid`, so the 43-char pattern lives in one place.

### 2.4 Password field

- `NEW_PASSWORD_POLICY` mirrors the server's (`server/src/auth/account-setup.ts`). A unit test reads `server/openapi/openapi.yaml` and pins `NewPassword` `minLength: 12` / `maxLength: 128` to it, so a server change that isn't mirrored fails `test:run`.
- Length is `password.length` (UTF-16 code units), the same count zod uses (MUT-235 C1), so client and server never disagree on the boundary.
- The rule ("Use 12 to 128 characters.") is the field's hint, always visible and wired with `aria-describedby`; a breach on submit becomes the field error, focuses the field, and sends nothing.
- No confirm field (the ticket asks for one field); the sign-in page's Show/Hide toggle guards against typos instead.
- `dir="ltr"` on the input, like sign-in.
- Username (D2): the email is a visible read-only `<input type="email" autocomplete="username" readOnly dir="ltr">` inside the form, before the password field. It is both the read-only email the ticket shows and the username field; no hidden field. Keychain and Chrome then save the pair; the `webcredentials` association offers it in the iPhone app.

### 2.5 After a successful redeem

Redeem revoked every session of this person (ADR-088), and the browser may hold someone else's session. So before setting `ME_KEY` the page calls `queryClient.clear()` (the in-memory cache is the only figure store), then `setQueryData(ME_KEY, me)`, `adoptAccountLocale(me.user.locale)`, `navigate({ to: '/', replace: true })`. Sign-in's own success path does the same minus the clear.

| state | heading | body | action |

| checking | — | loader "Checking your link" | — |

## Findings

Architecture
- A1 [P1] (9/10) src/hosted/queryClient.ts:22 — `queries: { staleTime: STALE_MS, retry: retryTransient }` with React Query's default `refetchOnWindowFocus: true`. After 30 s, coming back from a password manager or another tab re-runs the check; after a redeem the answer is `used`, so the page would swap the form (or the signing-in state) for the "used" card mid-flow, and every refocus spends the shared IP budget. Fix: the check query sets `staleTime: Infinity`, `gcTime: 0`, `refetchOnWindowFocus: false`, `refetchOnReconnect: false`, `retry: false`, and the page never re-derives its state from the check once a redeem has started. Necessary to deliver AC 2/5, carried without a question. Test: a focus event after 30 s sends no second check.
- A2 [P2] (9/10) src/hosted/session/SessionBridge.tsx:31 — `if (router.state.location.pathname === '/sign-in') return;`. Confirms the plan's exemption is needed: a sign-out in another tab would yank `/setup` to sign-in and lose the token. Already planned (§2.1).
- A3 [P2] (6/10, medium: verify in Safari) — a `hidden`/`display:none` username input is the Chromium-documented pattern, but WebKit's AutoFill is less predictable with fully hidden fields. A visible read-only `<input autocomplete="username">` carrying the email is the field every password manager reads. → D2.
- A4 [P2] (8/10) TD-149 — the ticket asks for a message; the page has the email and the typed password, so it could also try the sign-in itself. → D3.
- A5 [P3] (8/10) — a reload after the strip has no token. Plan §2.3 already adds the client-only `missing` message; correction only.

Code quality
- C1 [P3] (8/10) `tokenFromHash` doesn't need the "with or without #" branch: TanStack's `location.hash` never carries `#`. Trim and treat empty as null. Correction only.
- C2 [P3] (7/10) `NEW_PASSWORD_POLICY` duplicates the server constant across the server/portal package boundary; the OpenAPI drift test is the right guard (no shared module exists across that boundary). Accepted as planned.

Performance: no issues. One check, one redeem, one sign-in per link; A1 removes the only repeat-request path.
