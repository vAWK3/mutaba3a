# MUT-286 — Implementation plan: use the portal without an account

**Tracker:** Jira · barmajiyat.atlassian.net · MUT · status Backlog → In Progress once building starts.
**Epic:** MUT-284. **Blocked by:** MUT-285 (In Review, brief+ADR-097 approved and merged to local main `a77124f8`, not pushed) — unblocked for planning/building.
**Design authority:** `.claude/designs/mut-285-portal-local-mode.md` (approved brief) + ADR-097 (`.claude/DECISIONS.md`). This plan turns brief §2.3/§2.5/§2.6/§9/§13 into concrete files; it does not re-decide architecture.
**Siblings:** MUT-287 (expenses/groups/conversions/receipts, out of scope here), MUT-289/290/291/292 (later, unaffected by this plan beyond what they depend on).

## Scope recap (ticket ACs)

1. First visit → app opens in Arabic, no account.
2. Records survive reload and browser restart.
3. A parity test: one set of records through the server and through the local backend → identical statuses/totals.
4. Signed-out mode makes no `/v1` requests (network test asserts it). No FX exception applies yet — `GET /v1/public/fx-rates` is MUT-287.
5. Malafat suggestions / Malafat-linked profiles: signed-in only.

Plus Jira comment amendments (win over the description): D1 format version + migrations + CI fingerprint test + refuse-to-write-newer-format; D2 `navigator.storage.persist()` + Download/Restore in Settings; D3 is an MUT-287 concern, not built here; build order starts with the server refactor, behavior-preserving, full server suite green, before any browser code; session-expiry shows a choice, never a silent switch to local data.

**Assumption (flagging, not asking):** `PORTAL_ROUTES` (§2.3.3) is built as the single canonical list covering all 13 domains from the brief, including expense/group/conversion route factories — it is a mechanical registration list and splitting it across MUT-286/287 would create a second seam to keep in sync. `createLocalApp` passes `attachments: null` in MUT-286 (same "null = 503 ATTACHMENTS_NOT_CONFIGURED" contract every hosted profile without a bucket already gets), so expense/receipt endpoints exist but degrade exactly like an unconfigured hosted deployment until MUT-287 wires `LocalAttachmentStorage`. This keeps MUT-286 scoped to its ACs without a second server-route refactor in MUT-287. The expense **screens** themselves (list/create/edit, excluding the receipt-attach affordance) would therefore already work locally once routes are registered — since they're explicitly out of MUT-286's scope, Phase C's account/Malafat gating step (item 6) also hides the expenses/groups/conversions nav entries in local mode until MUT-287, so nothing half-works in front of a user.

## Phase A — Server refactor (behavior-preserving; lands first; full `server` suite + `openapi:check` green; no browser code yet)

1. **`server/src/app-shell.ts` (new).** `createApiShell(deps: { now: () => Date })`: returns `{ app: OpenAPIHono<AppEnv> }` carrying only `defaultHook`, a middleware that sets `c.set('requestId', ...)` / `c.set('now', now)` (request-id generation, no headers, no logging), `onError`, `notFound` — lifted verbatim from `app.ts:138-144,149-152,163-183`. `createApp()` calls `createApiShell({now})`, then adds its own `contextStorage()`, the CSP/`no-store`/logging middleware (`app.ts:147,153-161`), exactly as today — net zero behavior change, verified by the existing server suite passing unmodified.
2. **`server/src/routes/me.ts` (new).** Move `GET /v1/me` (`sessions.ts:109-123`) and `buildMe()` (`sessions.ts:233-251`) here as `meRoutes(store: LedgerStore)`. Export `ME_ORGANIZATION_INDEPENDENT_ROUTES = new Set(['GET /v1/me'])`. `sessions.ts` drops both, keeps sign-in/out/password/Malafat-suggestions (still needs argon2 via `auth/users.ts`), and its `ORGANIZATION_INDEPENDENT_ROUTES` drops `'GET /v1/me'`. Update `device-sessions.ts`'s import of `buildMe` to `../routes/me.js` (grep it first — device sign-in returns the same `Me` shape per its docblock). `app.ts` registers `meRoutes(store)` and unions `ME_ORGANIZATION_INDEPENDENT_ROUTES` into its existing set (`app.ts:202`).
3. **`server/src/routes/portal-routes.ts` (new).** `export const PORTAL_ROUTES: Array<(store: LedgerStore, deps?: ...) => OpenAPIHono<AppEnv>>` — one factory per: customers, projects, receivables, payments, summaries, attachments (needs the `{storage, urlTtlSeconds}` deps shape, not bare `store` — type the array entries accordingly or use a small discriminated wrapper), expenses (same attachments-deps shape), expense-categories, income, expense-groups, conversions, fx-rates (needs `CachedFxRates | null`), profiles, `meRoutes`. `app.ts` replaces its manual `app.route('/', xRoutes(store))` calls for exactly these with a loop over `PORTAL_ROUTES`, passing each factory its deps — **behavior-preserving**: same routes, same order where order matters (it doesn't for Hono route registration), same deps.
4. **Coverage test** `server/src/__tests__/portal-routes-coverage.test.ts` (new): parse every path literal `src/hosted/api/client.ts` calls (static list, hand-maintained from the 49-row table in the brief §3, not dynamically parsed from the client file — simpler and the brief already enumerated it) and assert each is answered by building a throwaway `OpenAPIHono` from `PORTAL_ROUTES` and checking `app.routes` includes `METHOD PATH`. Fails loudly if a future portal call isn't in the list.
5. **`MemoryLedgerStore.snapshot()` / `restore()`** (`memory.ts`): 
   - `snapshot(): LocalSnapshot` returns `{ formatVersion: CURRENT_STORE_SNAPSHOT_VERSION, maps: { orgs: this.orgs, custs: this.custs, ... } }` (all fields above except the six ephemeral ones) — Maps passed by reference is fine since callers (the IndexedDB persistence layer in Phase B) structured-clone them immediately into IndexedDB rather than holding the live references.
   - `restore(snapshot: LocalSnapshot): void` — for each named Map, `this.x.clear(); for (const [k,v] of snapshot.maps.x) this.x.set(k,v);`. Ephemeral fields stay empty/fresh (a restored store never replays old idempotency keys, sessions, or setup links — intentional per ADR-097 §2.3.4).
   - Update the class docblock: "for tests and the portal's local mode" (per brief §2.3.4).
   - This method lives in the **server** package so it's exercised by the server suite immediately; Phase B's browser persistence layer calls it, it doesn't reimplement it.
6. **Store-contract persisted variant** (`server/src/repositories/__tests__/store-contract-snapshot.test.ts`, new): seed a `MemoryLedgerStore` through a representative mutation sequence (customer, project, Owed income, a partial settle, an expense, a profile), `snapshot()`, construct a fresh store, `restore()`, assert reads (`customers.list`, `receivables.get`, `summaries.organization`) match the pre-snapshot store exactly.
7. **Two named memory/Prisma fixes (brief §4, review finding #2 — missing from an earlier draft of this plan, now explicit).** Both are pre-existing, documented differences the brief assigns to MUT-286 because the parity test (AC3) can't pass while they stand:
   - `memory.ts`'s `matchesExpense` (`memory.ts:1808-1817`) ANDs `unlinked` and `customerId` when both are set — requiring `e.customerId === f.customerId` **and** `e.customerId === null` simultaneously, which is never true, so memory always returns zero rows for that combination. **Correction to the brief's prose** (verified directly against `prisma.ts:1634-1642`, not taken on the brief's word — the brief says "Prisma lets `customerId` win," but the code's object-spread order is `customerId` (1639) then `unlinked` (1641), and a later spread key overwrites an earlier one, so Prisma actually lets **`unlinked` win**: the final `where` only has `customerId: null`, returning every unlinked expense regardless of the specific id requested). Fix `matchesExpense` to match: when `f.unlinked` is set, ignore `f.customerId` entirely (require only `e.customerId === null`), independent of whether `f.customerId` is also set. New case in the expenses store-contract file (`store-contract-expenses.ts`) asserting both-set behaves like `unlinked`-only.
   - Receivable `createdAt`: `memory.ts`'s `newReceivable()` (line 1364) sets `createdAt: input.postedAt`, where Prisma's three creation sites (`prisma.ts` adjustment/installment/retainer-charge) set `createdAt: at` as a field separate from `postedAt`. **Verified, not just taken from the brief:** checking all three memory-side callers (`memory.ts:992,1050,1190`) shows each already passes its own `at`/`now` value *as* `postedAt` — so `postedAt === at` holds everywhere in the current codebase, not only for Owed income. There is no live discrepancy to fix; threading a separate `at` parameter through `newReceivable()` to mirror Prisma's field choice exactly would touch every call site for zero behavior change, which is scope CLAUDE.md's "no refactoring for scenarios that can't happen" rules out. Instead: a store-contract case (`store-contract-m4.ts` or wherever receivable creation is covered) that asserts `receivable.createdAt` equals the `at`/`now` the test harness supplied, for each of the three creation paths — this locks the invariant as a regression test so a future caller that *does* diverge gets caught, without speculative production churn today.
8. **Platform shim test** `server/src/__tests__/platform-shim.test.ts` (new): import real `node:crypto`/`Buffer` and the Phase-B browser shims (`src/hosted/local/platform/crypto.ts`, relative import — this test runs under Node/Vitest so both sides are importable) and assert byte-identical output for SHA-256, HMAC-SHA256, base64url encode/decode round-trips, across ~10,000 randomized inputs (fixed seed for determinism). This test can only be finished once Phase B's shim files exist, so it's written and landed as part of Phase B, but is listed under "server suite" because it runs there.

**Gate before Phase B:** `npm --prefix server run typecheck && npm --prefix server run lint && npm --prefix server run openapi:check && npm --prefix server test` all green, with zero behavior change to any existing server test.

## Phase B — Local backend (`src/hosted/local/`, new directory)

1. **`src/hosted/local/platform/crypto.ts`, `async-hooks.ts`** — browser substitutes for the two Node touchpoints the shared route modules use (`randomUUID`, `randomBytes`, `createHash('sha256')`, `createHmac('sha256')`, `timingSafeEqual` from `node:crypto`; `AsyncLocalStorage` from `node:async_hooks`, needed only because `hono/context-storage` imports it at module scope even though local mode never calls `contextStorage()` — a real but inert `AsyncLocalStorage` polyfill, or the one Hono itself ships for non-Node runtimes if that exists, satisfies the import without behavior). `vite.config.ts`'s `hostedConfig()` gets `resolve.alias` entries mapping `node:crypto` → this file, `node:async_hooks` → that file, scoped to the hosted build only (the server's own `tsc` build and the main-app Vite config are untouched).
2. **`src/hosted/local/platform/buffer-shim.ts`** + a one-line install (`globalThis.Buffer = ...`) run before `createLocalApp` is constructed, covering `from(..., 'utf8'|'base64url')` / `toString('hex'|'base64url'|'utf8')` (cursors, preview tokens).
3. **`src/hosted/local/mintLocalSession.ts`** (new). **Corrected from an earlier draft (review finding #1 — BLOCKING): a session must be minted on every boot, not once.** `sessionsById` is one of the fields `snapshot()`/`restore()` deliberately excludes (ephemeral, server-identity concern) — so a restored store never has the session row a previous page load created, even though the person/org it belongs to *is* restored. Minting once-only would mean every reload after the first finds no valid `mds_` token, `GET /v1/me` 401s, and `AuthGate` redirects to `/sign-in` — breaking AC1/AC2 outright. Correct sequence, run on **every** boot before the first request:
   1. `store.users.findByEmail('local@device.invalid')` (or equivalent lookup) against the just-restored store. Not found → first-ever boot: `store.users.create` (locale from the app's current language, no password hash) + create the personal profile/organization (`slug`, `defaultCurrency`, `timezone` from `Intl.DateTimeFormat().resolvedOptions().timeZone` — all required by `CreateOrganizationInput`, `ports.ts:1179`; `slug` must be unique, e.g. a fixed constant since there is only ever one local org).
   2. Either way (found or just-created): mint a **fresh** device-session row this boot — `generateDeviceSessionToken()` + `sessionDigest(LOCAL_PEPPER, token)` (imported from `server/src/auth/sessions.ts`, unchanged) via `store.sessions.create(...)`, matching `CreateSessionInput`'s shape with no `verifiedPasswordHash`. This session lives only in the current `MemoryLedgerStore` instance for this page's lifetime — it is never persisted and never needs to be; each boot mints its own, cheaply.
   - **Deviation from the brief's prose:** this does *not* call the shared `signIn()` function, because `signIn()`'s whole job is verifying a password, and a from-scratch local person has none; it reuses the same token/digest primitives `signIn()` and `/v1/device-sessions` use, so the *verification* path (`authenticate()`) is still completely unmodified and sees an ordinary device session. `LOCAL_PEPPER` is a constant (not a secret — ADR-097 §2.2: "the local pepper and token protect nothing"). The resulting token is held in memory (module-level variable) for `transport.ts` (Phase B item 9) to attach as `Authorization: Bearer mds_…` on every local request — today's `client.ts:191-220` `request()` sets no `Authorization` header at all, since the cookie travels automatically; the local transport must add it explicitly.
4. **`src/hosted/local/createLocalApp.ts`** (new): `createLocalApp({ store, now }) => OpenAPIHono<AppEnv>` — calls `createApiShell({now})`, registers `PORTAL_ROUTES` + `meRoutes` over `requestScopedStore(store)` (reused as-is: inert guard, see research point 4, but keeps "same code path" true), passes `attachments: null` (assumption above), no `contextStorage()`, no CSP/logging middleware (meaningless for an in-page `fetch`-shaped call that never leaves the tab).
5. **`src/hosted/local/migrations/`** — `LOCAL_FORMAT_VERSION` constant + `index.ts` exporting an ordered list of `{from: number, to: number, migrate: (snap) => snap}` functions, run in sequence on load when `snapshot.formatVersion < LOCAL_FORMAT_VERSION`. Empty list at first ship (version 1, no migrations yet) — the mechanism exists before it's needed, per D1.
6. **`src/hosted/local/__tests__/format-fingerprint.test.ts`** (new, D1): derives a fingerprint (stable JSON of each persisted record type's key names + primitive types, sourced by reflecting over representative `ports.ts` record shapes used in the snapshot) and compares it to a checked-in constant; fails when a `ports.ts` record shape changes without a matching `LOCAL_FORMAT_VERSION` bump + migration. (Mechanical reflection over TS types isn't possible at runtime — this is implemented as a hand-maintained fixture object mirroring each record's shape, asserted structurally; the test's own diff is the enforcement, same spirit as a snapshot test.)
7. **`src/hosted/local/persistence.ts`** (new): `IndexedDbPersistence` — one DB `mut-local`, object store `state`, key `'snapshot'`. `load()`: read, run migrations if older, **refuse and signal "reload to continue"** if `formatVersion > LOCAL_FORMAT_VERSION` (never write). `save(snapshot)`: one `readwrite` transaction, `await` on `transaction.oncomplete` (not just the `put()` request) before resolving — this is what makes "durable before Saved" true. No custom serializer: IndexedDB's structured clone keeps `Map`, `Date` natively.
8. **`src/hosted/local/locks.ts`** (new): `withLock(fn)` wraps `navigator.locks.request('mut-local', {mode:'exclusive'}, fn)`. A `BroadcastChannel('mut-local')` posts after every successful write; a listener in Phase C invalidates the TanStack Query cache. Before each request, cheap read of `stateVersion`; if it moved, reload the snapshot first. **`src/hosted/local/__tests__/locks.test.ts`** (new, review finding #3 — the brief's §13.4 unit test was missing from an earlier draft): a fake IndexedDB (e.g. `fake-indexeddb`) and a fake `navigator.locks` drive two simulated backends racing a write to the same key; assert the loser reloads the winner's snapshot before applying its own change and no write is lost. This is the fast, deterministic test for the mechanism; `local.two-tabs` (release-QA) is the slow end-to-end confirmation, not a substitute for it.
9. **`src/hosted/local/transport.ts`** (new): `createLocalTransport(localApp, persistence, lock)` returns a `(req: Request) => Promise<Response>` matching `fetch`'s shape, performing: take lock → reload-if-stale → `localApp.fetch(req)` → on a mutating method (`POST|PATCH|PUT|DELETE`) with a 2xx/204 response, `persistence.save(store.snapshot())` and bump `stateVersion` → release lock → resolve with the `Response`. A tab closed mid-write means the IDB transaction aborts and nothing persists — the UI never showed "Saved" for that call, so nothing visible is lost.

**Gate before Phase C:** `npm run typecheck && npm run lint && npm run test:run` green for everything under `src/hosted/local/`; `server/src/__tests__/platform-shim.test.ts` (from Phase A item 7) green now that the shim files exist.

## Phase C — Client wiring

1. **`src/hosted/session/mode.ts`** (new): `getMode()/setMode('local'|'remote')` — one `localStorage` key `mut-mode`, try/catch wrapped, default `'local'` on any read failure. Set on a successful `api.signIn()` (→ `'remote'`) and on sign-out / a session-expired "Continue on this device" choice (→ `'local'`).
2. **`src/hosted/api/client.ts`**: `request()` (line 191) gains an injected transport, defaulting to today's same-origin `fetch`; when `getMode() === 'local'`, use `createLocalTransport(...)` (lazy — see item 5). `/v1/sessions` and `/v1/account-setup*` (sign-in, setup) **always** use real `fetch`, never the local transport, matching brief §2.6 ("`/sign-in` and `/setup` always talk to the server").
3. **`src/hosted/session/SessionBridge.tsx`**: today's unconditional 401→redirect-to-`/sign-in` becomes a choice screen (new `SessionExpired.tsx` under `src/hosted/session/`) offering "Sign in" (clears cache, navigates to `/sign-in`, mode stays `'remote'` until sign-in completes) or "Continue on this device" (sets mode `'local'`, clears cache, reloads into the local app) — **never** a silent switch. This only changes the *signed-in-session-expired* path; a fresh signed-out visit never 401s locally (the local `/v1/me` always answers).
4. **`src/hosted/session/AuthGate.tsx`**: no structural change — it already renders the app once `/v1/me` resolves and redirects to `/sign-in` on 401. In local mode `/v1/me` never 401s (the local person always exists after first boot), so first-visit behavior becomes "opens straight into the app," satisfying AC1 without touching this file's logic.
5. **Lazy local chunk**: `src/hosted/local/index.ts` barrel, dynamically `import()`-ed once (module-level promise, memoized) the first time `getMode() !== 'remote'` is known (app boot, before the first `api.me()` call) — signed-in users on a fresh session never trigger this import.
6. **Account/Malafat gating**: `src/hosted/shell/UserMenu.tsx` / `AccountDrawers.tsx` hide password-change and sign-out entries when `getMode() === 'local'`; Malafat-suggestion UI and Malafat-linked-profile affordances (`data/malafatSuggestions.ts`, wherever linked-profile chrome renders) gate the same way — satisfies AC5. (Grep call sites at build time; not re-enumerated here to avoid staleness.)
7. **Settings → Your data** (D2, Jira comment scope): new section, local-mode only — "Download my records" (serializes `store.snapshot()` + `LOCAL_FORMAT_VERSION` to a downloadable JSON file) and "Restore from file" (parses, runs migrations, confirms record count, calls `persistence.save()` + in-memory `restore()`). Call `navigator.storage.persist()` once, right after the first successful local save (fire-and-forget, result ignored per spec — browsers decide silently).

## Reuse / DRY check

No existing component or module does any part of this — it is new by nature (first local backend). Everything reused is explicitly named above: `authenticate()`, `writability.ts`, every route module, `requestScopedStore`, `sessionDigest`/`generateDeviceSessionToken`, the existing store-contract harness pattern, the existing server test harness pattern, `SessionBridge`'s existing 401 hook point (`setUnauthorisedHandler`), `AuthGate`'s existing render logic (no new gating needed there at all).

## Cost

$0 infra (client-side only in this phase; the one new server route is MUT-287). One-time ~136 KB gzip download for a signed-out visitor (measured in the MUT-285 spike), cached by the browser after first load; signed-in users never fetch it.

## i18n / RTL

New strings: the session-expired choice screen, Settings → Your data section (Download/Restore), any local-mode-only empty states. All through `src/hosted/i18n` (`ar.json`/`en.json`), Arabic default per ADR-077, RTL verified the same way existing portal screens are.

## Business / product impact

This is the load-bearing half of MUT-284: without it, retiring the free web app (the whole point of the epic) has nothing to retire *into*. It turns the portal into the one app for both a free, signed-out user and a paying hosted one, so every future feature is built once. It's what the MUT-289 upsell and MUT-290 account migration are built on top of — nothing downstream in the epic can start until clients/projects/income/payments work locally with the same figures as hosted.
