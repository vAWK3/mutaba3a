# Mutaba3a API — deployment runbook (Money v1 and the hosted portal)

Operator steps to take the hosted API from "code on main" to "a Partner can
connect from Malafat". Everything here runs on your machine, the way Malafat's
`pnpm release` does: Docker builds locally, migrations run locally through the
Cloud SQL Auth Proxy, Terraform applies from your shell. GCP only hosts the
result: one Cloud Run service, one Cloud SQL instance, a private attachments
bucket and three secrets. There is
no staging environment for now and nothing builds or migrates inside GCP
(ADR-026).

Time budget for the first deploy: about 40 minutes, of which Cloud SQL
creation is 10–15 minutes of waiting.

## 0. What you are deploying

| Piece | Name | Defined in |
|---|---|---|
| Cloud Run service | `mutaba3a-api` (min 1, max 1 instance) | `infrastructure/terraform/main.tf` |
| Cloud SQL Postgres 16 | `mutaba3a-pg`, db `mutaba3a`, user `mutaba3a_api`, REGIONAL, daily backups + PITR. After the MUT-381 cutover: `mutaba3a-pg2`, the same, encrypted with our own KMS key (§6d) | same |
| Secrets | `mutaba3a-api-database-url`, `mutaba3a-api-admin-token`, `mutaba3a-api-session-pepper` (MUT-38) — values generated by Terraform | same |
| Attachments bucket | `<project>-mutaba3a-attachments`, private; M6 attachments and MUT-42 expense receipts (`org/{id}/expense-receipts/…`) | same |
| Service account | `mutaba3a-api@<project>.iam` — `cloudsql.client`, accessor on its three secrets, object access on the bucket | same |
| Artifact Registry | `me-west1-docker.pkg.dev/<project>/mutaba3a/mutaba3a-api:<sha>` | same; image built by `scripts/deploy.sh` on your machine |
| Uptime checks + alerts | `GET /health`, `/ready` and the portal `/` every 5 min from six regions; email + SMS after 2 failed rounds, Cloud SQL disk/CPU alerts (MUT-328, §6b). Alerts only once `alert_email` / `alert_sms_number` are set | `infrastructure/terraform/monitoring.tf` |
| Hosted portal | `dist-hosted/` (MUT-45), baked into the same image at `/app/portal`, served by the same Cloud Run service — no separate domain, load balancer or Terraform resource | `Dockerfile`, `src/app.ts` |

The service issues and accepts **`live`** API keys (`config.API_KEY_ENVIRONMENT`).

`scripts/deploy.sh` is the only command per rollout. It builds the hosted
portal (`npm run build:hosted` at the repo root) and copies it into the Docker
context, builds the image with your Docker daemon, pushes it, runs `prisma
migrate deploy` from `server/` through the Cloud SQL Auth Proxy, applies
Terraform with the new tag, and runs `scripts/smoke.ts` against the API and
the portal both. If the migration fails the service is not touched.

The service runs **one instance** (`max_instances = 1`, validated in
Terraform) until TD-017 lands a shared rate-limit store. That is deliberate.

## 1. One-time prerequisites

### 1.1 Decide the GCP project

Two valid choices. Pick one and record it in `.claude/INFRA.md` (the first
production run on 2026-10-08 chose **`malafat-production`**; the resources
below exist there now):

- **Dedicated project** (recommended, e.g. `mutaba3a-prod`): clean ownership
  and billing for a product that will serve customers other than Malafat
  (ADR-024).
- **Malafat's project** (`malafat-production`): fewer moving parts; every
  resource name is prefixed `mutaba3a-` so nothing collides.

Either way the region is **`me-west1`** so firm data stays beside the CRM
(ADR-024 residency guarantee). Billing must be enabled on the project.

### 1.2 Tools on your machine

```bash
gcloud --version          # Google Cloud SDK
docker info               # Docker Desktop, daemon running
cloud-sql-proxy --version # brew install cloud-sql-proxy   (v2)
terraform version         # >= 1.9                          (brew install terraform)
node --version            # 22.x
```

Authenticate once; Terraform and the proxy use the application-default
credential, Docker pushes with your gcloud identity:

```bash
gcloud auth login
gcloud auth application-default login
gcloud config set project <PROJECT_ID>
gcloud auth configure-docker me-west1-docker.pkg.dev
```

Your account needs **Owner** on the project, or all of: `run.admin`,
`cloudsql.admin`, `cloudsql.client`, `secretmanager.admin`,
`artifactregistry.admin`, `iam.serviceAccountAdmin`, `iam.serviceAccountUser`,
`resourcemanager.projectIamAdmin`, `serviceusage.serviceUsageAdmin`,
`monitoring.editor`, `storage.admin`.

### 1.5 Sentry error reporting (one-time, ADR-091, MUT-147)

Separate from the GCP rollout: `server/infrastructure/sentry/` has its own
state, and `deploy.sh` never touches it. The rules are in
`docs/observability/README.md`.

1. **Org.** Use the company org **`barmajiyat-ltd`**, which is in the **EU
   (Frankfurt) region** (ADR-091 amendment 5). If you create it again, pick the
   EU region: the region can't be changed later. Never use an org outside
   Barmajiyat. Turn on **two-factor authentication on your own account first**:
   step 5 makes the org require it, and Sentry refuses that setting from an
   account without 2FA.
2. **Plan and budget.** Stay on the **Developer (free)** plan. Under
   Settings › Subscription, set the **pay-as-you-go budget to $0**, so overage
   is dropped and never billed, and keep Sentry's **quota notification emails**
   on. The free plan can't cap a key per day (ADR-091 amendment 8, TD-200), so this
   budget and spike protection are the only quota guards.
3. **Two tokens, two names** (D8).
   - **Admin token**, `SENTRY_ADMIN_TOKEN`: a **personal (user) auth token**
     (`sntryu_…`) created on your 2FA-enabled account, with `org:write`,
     `project:admin`, `team:admin` and `alerts:write`. An org auth token
     (`sntrys_…`) can't carry those scopes, and `require2FA` needs a user with
     2FA. Hand it to each command below. Never `export SENTRY_AUTH_TOKEN` with it: that name
     belongs to the upload token, and build tooling reads it.
   - **Upload token**, `SENTRY_AUTH_TOKEN`: an org auth token (`sntrys_…`) with
     release and upload scopes only, for MUT-149..151 builds. Store it once in the
     Keychain, where `make release server` reads it when the shell has none (MUT-149):

     ```bash
     security add-generic-password -U -s release-kit -a barmajiyat/SENTRY_AUTH_TOKEN -w
     ```

   Store neither in the repo, a tfvars file or the Flutter `.env`.
4. **Apply the projects, keys, alerts and spike protection:**

   ```bash
   cd server/infrastructure/sentry
   cp production.tfvars.example production.tfvars    # set organization (= the SENTRY_ORG in step 5) and the origins
   cp backend.hcl.example backend.production.hcl     # set bucket to the GCP state bucket, <PROJECT_ID>-terraform-state (§1.3)
   read -rs SENTRY_ADMIN_TOKEN                       # paste the admin token; it isn't echoed or exported
   terraform init -backend-config=backend.production.hcl
   SENTRY_AUTH_TOKEN="$SENTRY_ADMIN_TOKEN" terraform plan -var-file=production.tfvars
   SENTRY_AUTH_TOKEN="$SENTRY_ADMIN_TOKEN" terraform apply -var-file=production.tfvars
   ```

   The personal token reaches every org you belong to, and the step 5 guard runs
   after this apply. So before applying, read the org slug in the plan: every
   resource should show `organization = "barmajiyat-ltd"`.

   **If an earlier apply stopped with "inconsistent result" on `sentry_key`** (it did on
   2026-10-22, before ADR-091 amendment 8), the four keys are tainted. Keep them, and their
   DSNs, before planning again:
   `for s in api portal landing capture-app; do terraform untaint "sentry_key.this[\"$s\"]"; done`.

   **Two projects already exist.** You made `mutaba3a-web` (portal) and `mutaba3a-flutter`
   (capture app) by hand in Sentry's UI, so the plan shows them as **2 to import**, not
   to add. Terraform creates `mutaba3a-api` and `mutaba3a-landing`. The import may also
   show in-place changes on the two (team `mutaba3a`, allowed domains): that's expected.
   If the plan wants to *create* `mutaba3a-web` or `mutaba3a-flutter`, stop: the slug in
   Sentry differs from `local.surfaces` in `main.tf`.

   If the plan errors on `de.sentry.io`, or the apply stops on the "not in the
   EU region" postcondition, **stop and check the org's data region** in its
   settings. Never retry against `sentry.io`: that would hide an org created in
   the US (D5).
5. **Apply the org privacy settings.** The Terraform provider can't hold them,
   so this script sets them and reads them back. Before writing anything it
   refuses an org outside the EU region, and an org holding any project that
   isn't `mutaba3a-…` or `e33-…`, which catches a mistyped `SENTRY_ORG`. The settings
   are org-wide, so they apply to E33's projects too (ADR-091 amendment 9). Run it from the
   repo root:

   ```bash
   cd "$(git rev-parse --show-toplevel)"
   SENTRY_ADMIN_TOKEN="$SENTRY_ADMIN_TOKEN" SENTRY_ORG=barmajiyat-ltd npx tsx scripts/sentry-org-settings.ts --apply
   ```

   It prints the target org and host, then exits 1 and lists any setting that
   didn't stick. Re-run with `--check` whenever you want to confirm nobody
   changed them in the UI. Sensitive fields you add by hand are kept.
6. **Copy each DSN to its home** (the table in `docs/observability/README.md`):

   ```bash
   terraform -chdir=server/infrastructure/sentry output -json dsn
   ```

   The api DSN needs no copying: step 8 reads it from this stack's state. The
   portal's (`mutaba3a-web`) goes in `deploy.env` as `MUTABA3A_SENTRY_DSN=…` (MUT-149); with
   it set, `make release server` stops unless the upload token is there too (step 3). Before
   that release, `terraform -chdir=server/infrastructure/sentry plan` must show no
   `allowed_domains` change on `mutaba3a-web` (it must already list `https://app.mtb3a.com`);
   if it does, apply it first, or Sentry refuses every portal report. The landing's
   (`mutaba3a-landing`) goes to Netlify (step 9). Then `unset SENTRY_ADMIN_TOKEN`.
7. **Clean up the two hand-made projects.** Sentry gave each an automatic key with no rate
   limit and a default alert rule; Terraform can't remove either (it only sets `default_key
   = false` at creation). In `mutaba3a-web` and `mutaba3a-flutter`:
   - Settings › Client Keys: **revoke the key named `Default`**, keeping only the one named
     after the project (the capped Terraform key). The `mutaba3a-web` Default key is the DSN
     from Sentry's onboarding snippet, which has been pasted outside Sentry, so it must go.
   - Alerts: delete the default rule ("Send a notification for high priority issues" or
     similar), keeping the three Terraform alerts.

   **Read back.** In Sentry, confirm:
   - four projects, each with one key (no rate limit: the free plan can't set one);
   - the **Spike** alert's filter reads "more than 10 events in 1 hour" with no trigger, so it
     runs on every event. If Sentry shows it never fires, tell the team: it may need a trigger;
   - spike protection on;
   - three alerts per project;
   - the portal and landing projects' Allowed Domains.

   Then update INFRA's "Error reporting" Status row with the date.
8. **Turn the API's reports on (MUT-148).** In `server/infrastructure/terraform/production.tfvars`
   set `sentry_enabled = true`, then release (`make release server`). The release:
   - reads the api DSN from this stack's state (`terraform_remote_state`, no Sentry token), stores it as
     `mutaba3a-api-sentry-dsn` and mounts `SENTRY_DSN` and `SENTRY_ENVIRONMENT` into Cloud Run;
   - smoke-checks `/health`: expect `PASS  Error reporting matches the release — on vs on`;
   - hands pre-roll and post-roll the same DSN, so their crashes are reported too.

   Then send one deliberate event and find it in Sentry under `mutaba3a-api`:

   ```bash
   cd server
   SENTRY_DSN="$(gcloud secrets versions access latest --secret=mutaba3a-api-sentry-dsn --project="$GCP_PROJECT_ID")" \
     SENTRY_ENVIRONMENT=production SERVICE_VERSION="$(git rev-parse --short HEAD)" npm run sentry:smoke
   ```

   From then on `deploy.sh` refuses a release whose `production.tfvars` lacks `sentry_enabled = true`
   (it would delete the DSN secret). `SKIP_SENTRY_GUARD=1` only to turn reports off on purpose.

9. **Turn the landing's reports on (MUT-150).** Once, before the first release that carries them:
   - Dry run locally with the real values, so the release isn't the first run of the upload
     and the guard (eng O3):

     ```bash
     CONTEXT=production MUTABA3A_LANDING_SENTRY_DSN='<landing DSN>' SENTRY_AUTH_TOKEN='<sntrys_ upload token>' \
       npm run build:web && npx tsx scripts/check-bundles.ts --dist dist-web
     ```

   - Netlify › Site configuration › Environment variables, **Production context only**:
     `MUTABA3A_LANDING_SENTRY_DSN` = the landing DSN, and `SENTRY_AUTH_TOKEN` = the upload token
     (Keychain `release-kit` / `barmajiyat/SENTRY_AUTH_TOKEN`), marked **Contains secret values**.
   - `make release web`. On the live `/`, run `setTimeout(() => { throw new Error('MUT-150 smoke') })`
     in the console: the issue appears in `mutaba3a-landing` with a readable stack. Then open
     `/app` and check the network tab sends nothing to `sentry.io`.
   - If Sentry is down when a web release must ship (the upload would fail the build), remove
     `MUTABA3A_LANDING_SENTRY_DSN` from the production context, redeploy, and restore it after.

A new portal or landing origin (the custom domain, MUT-112) goes into
`portal_origins` / `landing_origins` followed by `terraform apply`. Until
then, that origin's errors are dropped.

## 2. Deploy

From a clean checkout of `main` (the script refuses uncommitted changes
anywhere in the repo, so the image tag always names a commit; `make release
server` fails its preflight on them before anything is committed or pushed):

```bash
cd server
npm ci
export GCP_PROJECT_ID=<PROJECT_ID>
export TF_STATE_BUCKET=<PROJECT_ID>-terraform-state
./scripts/deploy.sh
```

What you will see, and what to answer:

1. `terraform init` against `gs://…/mutaba3a-api/production`.
2. A targeted plan that creates the Artifact Registry repository, the Cloud SQL
   instance, database and user, and the database-URL secret → **yes**.
   Cloud SQL takes 10–15 minutes (about 5 on a quiet day). The two warnings
   `Resource targeting is in effect` / `Applied changes may be incomplete` are
   expected here: this first apply is deliberately partial because the image
   has to be pushed and the database migrated before the service can start.
   Step 5 is the complete apply.
3. `docker build --platform linux/amd64` on your machine, then `docker push`
   of `mutaba3a-api:<sha>` (first build 2–4 min; later builds are cached).
4. `cloud-sql-proxy` starts on `127.0.0.1:5440`, `prisma migrate deploy` runs
   from `server/` against production, output ends with
   `All migrations have been successfully applied`, the proxy stops.
5. The full plan: service account + IAM, admin-token secret, Cloud Run
   service, public invoker, uptime checks (alerts once §6b is set) → **yes**.
6. `smoke.ts` runs the unauthenticated checks and prints `smoke: all checks passed`.
7. The proxy starts again and `npm run post-roll` repairs rows the old revision
   wrote after the migration (MUT-61: a person's payment must be `origin
   CAPTURE`) and gives any user without one a personal profile (MUT-120
   shipped with no backfill). Normally prints `post-roll: 0 captured payment(s)
   re-marked origin CAPTURE` and `post-roll: 0 personal profile(s) backfilled,
   0 skipped`; the proxy stops. A `still has no personal profile` warning names
   a user to provision by hand. Since MUT-254 it also links expenses to their
   vendors (`post-roll: vendors — N expense(s) linked, …`): the first deploy
   with the vendors migration links every existing expense; later runs link
   only what the old revision wrote during the roll (normally 0). The same
   step by hand: `DATABASE_URL=… npm run backfill:vendors -- --dry`, then
   without `--dry`.
8. The last line is the service URL: `https://mutaba3a-api-….a.run.app`. Keep it.

Repeat runs are the same command; plan 2 shows no changes and the service
rolls to the new tag. Pass `AUTO_APPROVE=1` once you trust it.

### 2.1 If a step fails

The script stops at the first error (`set -e`) and prints `[deploy] …` in red.
Nothing it has already created is lost, and **re-running `./scripts/deploy.sh`
is always the recovery**: Terraform reconciles only what is missing, Docker
reuses the cached layers, the registry already holds the tag, and
`prisma migrate deploy` finds `No pending migrations`. Do not run `terraform
destroy` or delete resources by hand to "start clean"; the Cloud SQL instance
has deletion protection and a fresh one costs another 10 minutes.

| Where it stopped | What exists | What to do |
|---|---|---|
| Step 2 (Cloud SQL) | possibly a half-created instance | wait a minute, re-run; Terraform picks the instance up from state |
| Step 3 (docker) | nothing new | fix Docker (daemon, auth: `gcloud auth configure-docker me-west1-docker.pkg.dev`), re-run |
| Step 4 (migration) | image pushed, database untouched or partially migrated | read the Prisma error; the service was **not** rolled. Fix the migration, commit, re-run |
| Step 5 (full apply) errors on `google_cloud_run_v2_service.api` | database migrated, secrets and service account created, **no service** | fix the Terraform error (below), re-run. `terraform output service_url` does not exist until this step succeeds, so §3 cannot run yet |
| Step 6 (smoke) | everything, service URL printed | the service is up but a check failed; read the `FAIL` line, see §6 for logs |

The failure the first production run hit on 2026-10-08 was step 5:

```
Error 400: template.containers[0].env: The following reserved env names were
provided: PORT. These values are automatically set by the system.
```

Cloud Run sets `PORT` to the declared `container_port` (8787) itself and
refuses a template that also lists it. The `PORT` env entry was removed from
`main.tf` in the fix that accompanies this note; the service reads the
injected value through `config.PORT`. If you see this error you are on an
older commit: pull `main` and re-run.

After a step-5 failure the symptoms downstream are: `terraform output -raw
service_url` says `Output "service_url" not found`, and if you then run
`npm run smoke -- --url "$URL"` with that empty `URL`, the smoke script exits
with code 2 and `--url is empty …` (older builds crashed with
`Failed to parse URL from /health`, which meant the same thing).


## 4. Provision the first firm

Keys are operator-issued (TD-018, Accepted). The secret is
printed **once**; hand it to the Partner over a secure channel, never by email
or chat.

```bash
npm run provision -- --url "$URL" \
  --name "Sader Law Firm" --currency ILS --timezone Asia/Jerusalem --key-name "Malafat"
```

Output: `organization sader-law-firm = <uuid>` and the key
`mut_live_<prefix>_<secret>`. The key carries every scope Malafat needs;
`GET /v1/integration` will report `missingScopes: []`.

To issue a second key later (rotation is also possible from Malafat's settings
page): `npm run provision -- --url "$URL" --organization-id <uuid> --key-name "Malafat (rotated)"`.

### 4a. Refresh Malafat's vendored contract

Malafat vendors a copy of this API's contract. A test fails when its client
calls a path, method or field the copy lacks. Refresh it from the deployed
`main` commit, never from a feature branch, so the file names a commit that
exists on the remote. Do it whenever a deploy changes `openapi/openapi.yaml`.

```bash
cd server
npm run -s openapi:json > /path/to/crm-platform/apps/web/src/features/money/contract/mutaba3a-openapi.json
node -e "JSON.parse(require('fs').readFileSync(process.argv[1],'utf8')); console.log('valid')" /path/to/crm-platform/apps/web/src/features/money/contract/mutaba3a-openapi.json
```

Three traps, all hit on 2026-10-11:

- **Run it from `server/`.** The repository root has no `openapi:json`
  script, and npm answers `Missing script: "openapi:json"`.
- **The shell empties the target before npm starts.** A failed run leaves
  Malafat's file at 0 bytes. Re-run correctly before committing anything in
  Malafat.
- **Keep `-s`.** Without it npm writes its `> @mutaba3a/api … openapi:json`
  banner to stdout, so the file starts with two lines that aren't JSON and
  Malafat's contract test fails to parse it. The `node -e` line above catches
  this.

Then, in Malafat, run the Money contract test and commit the file in the next
web release.

Sessions (MUT-38) added the audit actor `USER` (ADR-037 decision 9). Add
`"USER"` to the `actorType` union in Malafat's
`apps/web/src/features/money/domain/types.ts`. Malafat's client does no
runtime validation and its history view only tests `actorType === "SYSTEM"`, so
a `USER` row cannot break a release that lacks it (checked 2026-10-11). That is
why the 2026-10-11 deploy could go out before this refresh.

### 4b. Give a person access to the hosted portal (MUT-37)

The service reads `SESSION_TOKEN_PEPPER` from the Secret Manager secret
`mutaba3a-api-session-pepper`, which Terraform generates and mounts (MUT-38).
The first `./scripts/deploy.sh` after this change creates it; nothing to do by
hand.

Portal users are operator-issued exactly like keys (ADR-037, TD-018): there is
no signup, invite or "forgot password" route in any environment. Since MUT-235
(ADR-088) the operator never handles a password: `provision:user` prints a
one-time **setup link** **once** (72 hours; `--valid-hours 1–720`). Deliver it
like a key secret. The person sets their own password through it on the portal's
`/setup` page (MUT-236) and then signs in on the portal or the app.

```bash
npm run provision:user -- --url "$URL" --email nour@firm.ps --name "Nour Haddad" \
  --organization-id <uuid> --locale ar
```

The guided way, from the repo root, fetches the token and URL itself, asks for
the rest, shows a summary and confirms before calling the API:

```bash
make create user        # a person with their personal profile; may join an existing firm
make create business    # a new firm (§4, key optional: `provision --no-key`), then its first person
```

Both are `server/scripts/provision-account.sh user|business`.

Every user is also created with exactly one personal profile (MUT-120). With no
firm, pass `--currency` and `--timezone` instead of `--organization-id`; with a
firm they default to the firm's. A personal profile is never shared, issued an
API key or bound to Malafat (409 `CONFLICT`, `reason: PERSONAL_PROFILE`).

A person in two firms gets a second membership:
`npm run grant:user -- --url "$URL" --email nour@firm.ps --organization-id <uuid>`.
Every account change is audited as `ADMIN` on each organization the person belongs
to, their personal profile included (`user.created`, `membership.granted`,
`membership.revoked`, `user.setup_link_issued`, `user.disabled`, `user.enabled`; the
personal profile also gets `organization.created`). When the person sets their
password through a link, `user.password_set` is audited as `USER`. Events from before
MUT-235 keep the old action `user.password_reset`.

As of MUT-45, the portal is live at the service's own URL (`$URL/`) — a
provisioned person can sign in there directly; `POST /v1/sessions` and
`GET /v1/me` remain available for API-level checks (README "Sessions").

### 4c. Cookies, CORS and CSP (MUT-45) — what is set and why

The portal and the API are **one origin**: the same Cloud Run service serves
both (`src/app.ts`, hosted-portal.md §9), so there is nothing to configure for
cookies or CORS beyond what MUT-38 already built:

- **Cookie**: `__Host-mut_session`, `Secure`, `HttpOnly`, `SameSite=Strict`.
  `__Host-` requires same-origin-only, HTTPS-only delivery — exactly what a
  single-service deployment gives for free (ADR-037 decision 3).
- **CORS**: none. A cross-origin page cannot read the session cookie or call
  `/v1/*` with it; there is no `Access-Control-Allow-Origin` to misconfigure,
  because there is no second origin to allow.
- **Same-origin check for non-GET session requests**: `PORTAL_ORIGIN` is
  intentionally **unset** in production. `isSameOriginRequest()`
  (`src/auth/sessions.ts`) then compares the request's `Origin` header against
  the URL it actually arrived on, which is correct and sufficient as long as
  nothing in front of Cloud Run changes the apparent origin — true today,
  since there is no custom domain. The custom domain's front door (§5a, ADR-155)
  sets `PORTAL_ORIGIN` together with `FRONT_DOOR_TOKEN`: requests carrying the
  token are checked against `PORTAL_ORIGIN`, direct run.app requests against
  their own origin, so both hosts work during the move.
- **CSP**: `default-src 'self'; connect-src 'self' https://storage.googleapis.com
  https://eu.i.posthog.com; img-src 'self' data:; frame-ancestors 'none'; form-action 'self'` on every
  response. `'self'` everywhere else is possible precisely because the portal
  and the API share an origin; `frame-ancestors 'none'` blocks the portal from
  being framed anywhere; `form-action 'self'` and no `script-src` relaxations
  keep the policy as tight as the app allows without inline scripts or
  third-party calls. The one addition to the design brief's draft policy is
  `https://storage.googleapis.com` in `connect-src`: receipt uploads (MUT-44)
  `fetch()` a `PUT` directly to a GCS v4 signed URL — `storage.googleapis.com`
  is the library's default, path-styled host (`@google-cloud/storage`'s
  `PATH_STYLED_HOST`, `virtualHostedStyle` not set) — and `connect-src` governs
  that call. Receipt *downloads* need no entry here: `downloadNavigator.open()`
  is a top-level navigation, which `connect-src` does not restrict. MUT-260
  (ADR-193) adds the same host to `img-src` and `frame-src` (plus `'self'` in
  `frame-src` for the dev server's same-origin local driver): the Receipts tab
  shows a receipt's original inline, an `<img>` or an `<iframe>` of a PDF signed
  with `?disposition=inline`. Signed URLs live minutes on their own origin, so a
  receipt can never script the portal. The second
  addition is `https://eu.i.posthog.com` (MUT-155, ADR-090): the portal's
  opt-in anonymous usage counts post to PostHog's EU host, and only after the
  signed-in person turns sharing on. The SDK ships in the portal's own bundle,
  so `script-src` needs nothing. The counts also need `dist-hosted` built
  with `MUTABA3A_POSTHOG_KEY`; without it the portal never asks and never sends.

### 4d. App association files (MUT-111) — what is set and why

iOS only trusts the portal's saved passwords and opens portal links in the app
once the domain declares it via `GET /.well-known/apple-app-site-association`;
Android needs the same declaration via `GET /.well-known/assetlinks.json`.
Both are served by the API itself (`src/routes/well-known.ts`), generated from
config so a domain move (MUT-112) changes no code.

- **Config**: `apple_team_id`, `apple_bundle_id`, `android_package_name` and
  `android_sha256_fingerprints` (Terraform variables, `production.tfvars`) —
  all four or none; a `terraform plan` precondition and `config.ts`'s own
  boot-time check both refuse a partial set. Empty (the default) disables both
  routes entirely — same "absent dependency" shape as `PORTAL_DIST_DIR` and
  `ATTACHMENTS_BUCKET`.
- **Adding a fingerprint**: `android_sha256_fingerprints` is a comma-separated
  list (the debug and upload-key fingerprints at minimum, MUT-114; the Play
  App Signing fingerprint joins later, in the Android epic). Edit the value in
  `production.tfvars`, `terraform apply`, done — no code change, no redeploy
  of the image itself (only the Cloud Run revision's env vars change).
- **Moving domains** (§5a): nothing changes here. Both files are host-free, so
  the front door serves them on `app.<apex>` as-is, and run.app keeps serving
  them for old app builds (the legacy redirect never touches `/.well-known/*`).
  The phone must claim both hosts for a release (§5a step 5).
- **Apple's CDN caches the AASA for up to about 24 hours.** A fingerprint or
  path-list change deployed just now will not necessarily be visible to a
  freshly-installed iOS app immediately — don't assume a redeploy is broken
  just because Apple's side hasn't refreshed yet.
- **Verifying it actually works is a manual, post-deploy step** — no test in
  this repo's suite calls Apple or Google's live infrastructure. After a
  deploy that touches these routes, run the live `run.app` URL through:
  - Apple's AASA validator (e.g. `https://search.developer.apple.com/appsearch-validation-tool/`)
  - Google's Digital Asset Links API tester
    (`https://developers.google.com/digital-asset-links/tools/generator`)

  Both must pass before MUT-113 (iOS) or MUT-114 (Android) can be verified
  end to end.

## 5a. Moving to the custom domain (MUT-326 prepares, MUT-112 runs it)

**Everything below reads one file: `config/hosts.json`** (ADR-155). It holds:

- `domain`: the apex, `null` until it is chosen.
- `portalSubdomain`: `app`, so the portal and API move to `app.<apex>`.
- `legacy`: today's run.app and netlify.app origins. They keep answering throughout the move.
- `stage`: one of `legacy` → `proxy` → `live` → `redirect`.

Picking the domain is the one edit; each later step moves `stage` on by one. The landing goes
to the apex. To see what any change does before you make it, run:

```bash
npm run domain:plan -- --domain example.com --stage live
```

It prints every consumer's value now and after: vite defaults, Netlify redirects, Cloud Run
env, front door, Sentry, the uptime host, the exact phone `.env` / entitlements / manifest
lines, and Malafat.

**Why a Worker, and why a token (ADR-155):**

- **Cloud Run domain mapping isn't offered in `me-west1`.** So `app.<apex>` is a Cloudflare
  Worker (`server/infrastructure/frontdoor/worker/front-door.js`) in front of the run.app URL,
  like Malafat's `malafat-router`. Free up to 100,000 requests a day per Cloudflare account.
- **run.app stays reachable directly** for old phone builds, Malafat and the carry-over. The
  front-door path has one more hop than the direct path, so a single `TRUSTED_PROXY_HOPS` can't
  key sign-in throttling correctly on both.
- **The token solves that.** The Worker sends `FRONT_DOOR_TOKEN` and the client IP Cloudflare
  read, and the server trusts that IP only when the token matches. `TRUSTED_PROXY_HOPS` stays 1.

### What you need first
- **The domain, bought.** Cloudflare Registrar is the simplest, because the zone then already
  exists (see the import note in step 1).
- **A Cloudflare account, chosen on purpose.** The Workers free tier is per account: on
  Malafat's account it is shared with `malafat-router`.
  - API token scopes on that account: Zone Edit, DNS Edit, Zone Settings Edit, Workers Scripts
    Edit, Workers Routes Edit. Export it as `CLOUDFLARE_API_TOKEN`.
- **A Netlify personal access token**, exported as `NETLIFY_API_TOKEN`.
- **The Netlify site id** of the landing (Site settings › Site details).
- **`server/infrastructure/frontdoor/production.tfvars`**, copied from the `.example` and filled
  in with `project_id`, `cloudflare_account_id` and `netlify_site_id`.

### Step 0: name the domain (`stage: "proxy"`)

In `config/hosts.json`, set `"domain": "<apex>"` and `"stage": "proxy"`.

```bash
npm run domain:plan -- --stage proxy
npm run test:run -- scripts/__tests__/no-hardcoded-hosts.test.ts
```

Read the plan, then commit. At this stage no build changes: vite, the terms guard and the phone
still use the legacy hosts. A release made now ships nothing new.

### Step 1: DNS (front-door stack)

```bash
cd server/infrastructure/frontdoor
terraform init -backend-config="bucket=${TF_STATE_BUCKET}" -backend-config="prefix=mutaba3a-frontdoor/production"
# Bought at Cloudflare Registrar? The zone exists already: import it first.
#   terraform import -var-file=production.tfvars 'cloudflare_zone.this[0]' <zone id>
terraform plan -var-file=production.tfvars -out=frontdoor.plan
terraform show -json frontdoor.plan | jq -r '.resource_changes[] | select(.change.actions != ["create"] and .change.actions != ["no-op"]) | "\(.change.actions) \(.address)"'
```

The `jq` line must print **nothing**: the first plan only adds. On a placeholder domain it reads
`16 to add, 0 to change, 0 to destroy`. Then:

```bash
terraform apply frontdoor.plan
terraform output name_servers
```

Set those name servers at the registrar, then wait until Cloudflare shows the zone **Active**:

```bash
dig +short NS <apex>
```

### Step 2: certificates

- **Portal host:** Cloudflare's edge certificate for `app.<apex>` is automatic.
- **Apex and `www`:** Netlify issues their certificate once DNS resolves to it (the apex is a
  flattened CNAME to `apex-loadbalancer.netlify.com`, DNS only). If it doesn't, use Netlify ›
  Domain management › HTTPS › Verify DNS configuration.

Then check all three:

```bash
curl -sI https://<apex>/ | head -1
curl -sI https://www.<apex>/ | head -1
curl -s https://app.<apex>/health
```

### Step 3: proxy, then the server learns the token

```bash
make release server
```

Same `stage: proxy`, so the build is unchanged. Terraform adds `PORTAL_ORIGIN` and
`FRONT_DOOR_TOKEN` to Cloud Run; its data source fails loudly if step 1 wasn't applied. Then
check the front door end to end:

```bash
curl -s https://app.<apex>/health
curl -s https://app.<apex>/ready
curl -s https://app.<apex>/.well-known/apple-app-site-association | head -c 200
curl -s https://app.<apex>/.well-known/assetlinks.json | head -c 200
npm --prefix server run smoke -- --url https://app.<apex>
```

Then sign in on `https://app.<apex>`. The session cookie is per origin, so expect to sign in
there separately.

**Nobody is sent to the new hosts before this works.**

### Step 4: go live (`stage: "live"`)

In `config/hosts.json`, set `"stage": "live"`, run `npm run domain:plan`, and commit. Then
release in this order:

```bash
make release web
make release server
```

**Web first.** The landing builds canonical/og tags for the apex. Its `_redirects` sends
`<apex>/app/*` back to `netlify.app/app`, because the free web app's records live in that
origin's IndexedDB until MUT-291.

**Then the server.** The portal bundle links to the apex's `/terms`, and the terms guard reads
`https://<apex>/legal/terms-versions.json`, so wait for Netlify's deploy first. `deploy.sh` now
also smoke-tests `public_portal_origin`.

Then:
- **Sentry:** re-apply the Sentry stack (§1.5) so the DSNs accept the new origins.
- **Uptime:** the checks follow `local.public_portal_host` (MUT-328).
- **PostHog:** check the pilot tiles' `$host` filters (MUT-330).

### Step 5: phone release with both hosts (mutaba3a-flutter repo)

Copy the lines `npm run domain:plan` prints under **7. Phone**:

- **`.env`:** `MUTABA3A_API_BASE_URL` and `MUTABA3A_PORTAL_BASE_URL` = `https://app.<apex>`;
  `MUTABA3A_PUBLIC_ORIGIN` = `https://<apex>`.
- **`ios/Flutter/AssociatedDomains.xcconfig`:** `MUTABA3A_LINK_HOST`.
- **`Runner.entitlements`:** one `applinks` + `webcredentials` pair **per host**, new and run.app.
- **`AndroidManifest.xml`:** `android:host` per host and path.
- **`strings.xml` `asset_statements`:** both hosts' `assetlinks.json`.

Keep the run.app host for at least one release: old links and passwords saved against run.app
keep working only while it is claimed. Apple's CDN caches the AASA for up to about 24 hours.

### Step 6: redirect the old hosts (`stage: "redirect"`)

**Only after the carry-over (MUT-291, ADR-185) has shipped and been checked.** Before that, a
redirect strands signed-out local-mode records on run.app. In order:

1. `make release server`: ships the receiver (`/carry-over/receive` on the new host) and the old
   host's `/carry-over` page. Both are inert until someone opens them.
2. `make release web`: ships the free web app's carry-over screen. From now on, every visit to
   `netlify.app/app` with records offers the move (MUT-291 D1).
3. **Day-7 check (operator):** in one real browser holding free-app records, carry them to the
   live new host and compare the summary's totals with the old app's own screens. Do the same
   from run.app signed out, if you have local records there.
4. Then this step.

In `config/hosts.json`, set `"stage": "redirect"`, commit, then:

```bash
make release web
make release server
```

- **Netlify:** 302s the old host's landing pages (`/`, `/download`, `/privacy`, `/terms*`) to
  the apex. Never `/app/*`.
- **Cloud Run:** gets `PORTAL_LEGACY_REDIRECT=true`. Direct run.app page visits go to the
  same-origin `/carry-over?next=…` page, which carries local records over and then sends the
  browser on.
- **Never redirected on run.app:** the API (`/v1/*`), `/admin/*`, the association files,
  `/health`, `/ready`, `/assets/*`, static files and writes.
- **Then, in the next phone release (Flutter repo):** drop `MUTABA3A_LEGACY_LINK_HOST` (xcconfig,
  entitlements, the Android manifest and `asset_statements`, the guard test). Not before: until the
  redirect is live, run.app links still exist and the phone opens them.

Check it:

```bash
curl -sI https://<run.app host>/sign-in | grep -i location
curl -sI https://<run.app host>/v1/me | head -1
```

The first must show `/carry-over?next=%2Fsign-in`. The second must still be `401`, not a redirect.

### Rollback (any step)

| From | Undo |
|---|---|
| 6 | `stage: "live"`, then `make release web` and `make release server`. 302s are never cached, so visitors return to the old hosts at once |
| 5 | Ship the phone again with the run.app values. The old host was never unclaimed |
| 4 | `stage: "proxy"`, then `make release web` and `make release server`. Users are back on the legacy hosts; the front door still works |
| 3 | `stage: "legacy"` and `domain: null` in a **branch you deploy from**, then `make release server`. Cloud Run drops `PORTAL_ORIGIN` and `FRONT_DOOR_TOKEN` and the IAM grant; the server behaves exactly as before |
| 1–2 | Leave the frontdoor stack applied: unused, it costs nothing. To remove it, lift `prevent_destroy` on the zone and the token secret, then `terraform destroy`. `cloudflare_zone_setting` can't be destroyed from Terraform (the provider says so) and stays with the zone |

Order matters on the way back: undo the API stack (step 3) before destroying the frontdoor
stack. Cloud Run reads the token secret by name, so deleting it first breaks the next cold start.

### What doesn't move
- **Malafat** calls `/v1` on run.app, which answers for good. Switching
  `malafat-web-mutaba3a-api-url` to `https://app.<apex>` is optional.
- **The Malafat OAuth client identity** (`CIMD_CLIENT_ID`, `public/.well-known/oauth-client.json`)
  is `https://mtb3a.com/.well-known/oauth-client.json` (MUT-387), a fixed literal that never
  follows `config/hosts.json`. Serving it is **not** config-independent, though:
  - The zone (`frontdoor/main.tf`, `cloudflare_zone.this`) and the Netlify custom domain
    (`netlify_site_domain_settings.landing`) are built from the config's domain. A later apex
    change must keep `mtb3a.com` bound to the Netlify site (an alias, or a manual step) and keep
    its zone, or the document 404s.
  - `mtb3a.com` must stay the site's primary domain. With `www` as primary, Netlify 301s the
    apex, and Malafat refuses any 3xx (`cimd-fetcher.ts`).
  - The apex record stays DNS-only, with no Worker route or redirect rule. The vite-config test
    keeps Netlify's own rules off the path at every stage, and `make release web` checks the
    live document after every deploy (`npm run release:oauth-client`; run it with
    `OAUTH_CLIENT_WAIT_SECONDS=0` any time).
  - Keep or remove the zone's apex record and the Netlify domain binding **together**. An apex
    record still pointing at Netlify after the binding is gone is a dangling record: whoever adds
    `mtb3a.com` to their own Netlify site then serves a client document under our id.
  - Rollback rows 1–2 and the planned Cloudflare-account split take the document offline until
    the zone is back. Nothing calls the flow today (TD-075), so no user notices.
- **Browser-saved passwords** in Safari/iCloud Keychain and Chrome are tied to run.app. They
  aren't offered on `app.<apex>`, so people sign in once and their browser saves the new host.
  The phone app keeps offering them through `webcredentials` for both hosts. Google Password
  Manager could link the two hosts through web↔web statements in `assetlinks.json`, an API
  contract change left to MUT-112. Say so in MUT-112's release note.

### Passkeys (MUT-115, ADR-190)

Passkeys are bound to their relying-party ID **for life**, so it is the apex (`mtb3a.com`), never a
subdomain or the run.app host. One RP ID serves both the portal (origin `https://app.<apex>`) and the iOS
app (native assertions carry `https://<apex>`).

- **Server:** Terraform's `domain.tf` sets `WEBAUTHN_RP_ID = <apex>` from stage `live`. The allowed origins
  default to `PORTAL_ORIGIN` and `https://<apex>`; the server refuses to start if either is outside the RP ID.
  Unset (stages `legacy`/`proxy`, or staging), every passkey route answers 404 and the portal hides passkeys.
  The portal also hides them on the legacy run.app host (a passkey made there would be useless).
- **Apex `apple-app-site-association`:** iOS checks `webcredentials` on the RP ID itself. The apex is the
  Netlify landing, so the web build's `_redirects` proxies `https://<apex>/.well-known/apple-app-site-association`
  to the portal's own file with a **200** (Apple refuses a redirect). The server's `APPLE_TEAM_ID` /
  `APPLE_BUNDLE_ID` stay the one source. Check after a web release:
  `curl -sI https://<apex>/.well-known/apple-app-site-association` (200, `application/json`), and before a
  phone release Apple's CDN copy: `curl -s https://app-site-association.cdn-apple.com/a/v1/<apex>`.
- **Local dev and QA:** `WEBAUTHN_RP_ID=localhost` and `WEBAUTHN_ORIGINS=http://localhost:<port>,https://localhost`.
- **Order:** web (the AASA rewrite), then server (turns passkeys on), then the phone once Apple's CDN shows
  the apex file.

### 6a. Pilot: entries per profile and per user (MUT-330)

The weekly pilot review (`docs/commercial/pilot-reviews.md`) and the GA
go/no-go (`docs/commercial/pilot-metrics.md`) need two numbers per pilot user:
did they record a first income or expense within 7 days of setup, and in how
many of the last 4 weeks did they record anything. This is the record of
those numbers. PostHog dashboard 1031822 only sees people who opted in, so it
undercounts.

**Rules (ADR-024):**
- The session is **read-only**: `PGOPTIONS` makes every transaction read-only,
  so a slip can't write. `SHOW default_transaction_read_only;` must say `on`.
- The output stays on your screen. **Never send it anywhere:** not into chat,
  a ticket, a spreadsheet, PostHog or this repository. Only the pilot codes
  and counts go into `pilot-reviews.md`, never an email or a profile name.

**Pilot codes.** Keep the ten pilot emails, in signup order, in a file outside
the repository, for example `~/.mutaba3a/pilot-users.psql`:

```
\set emails 'first@example.com,second@example.com'
```

The first email is `P01`, the second `P02`, and so on. Only append to the
list; never reorder it, or the codes in past reviews change meaning. No
spaces between emails.

**Run it:**

```bash
cd server && PGOPTIONS='-c default_transaction_read_only=on' TF_STATE_BUCKET=<bucket> npm run db:psql
```

Then, in psql:

```
SHOW default_transaction_read_only;
SET TIME ZONE 'UTC';
\i ~/.mutaba3a/pilot-users.psql
\set as_of now
```

`as_of` is the end of the window. Leave it at `now` for the weekly review. For
the GA verdict, set it to the pilot's last day, for example
`\set as_of '2027-01-31 23:59'`.

What counts as an entry (the same three kinds the entries feed shows as
income or expense, MUT-270):
- an expense that isn't deleted;
- a captured payment (Received: `payments.origin = 'CAPTURE'`, still
  `POSTED`; an undone one is `REVERSED`);
- an Owed entry (`receivables.origin = 'ADJUSTMENT'`, not deleted).

Malafat's payments (`INTEGRATION`), conversions and unsorted inbox entries
don't count. An entry counts in the week it was **logged** (`createdAt`), not
the date it's for. **Setup** is the person's first terms acceptance, which the
setup link records (ADR-102), or the account's creation if there's none.

```sql
-- 1. Entries per profile (organization), pilot users' profiles only.
WITH pilot AS (
  SELECT u.id, u.email, 'P' || lpad(array_position(string_to_array(:'emails', ','), u.email)::text, 2, '0') AS code
  FROM users u
  WHERE u.email = ANY (string_to_array(:'emails', ','))
),
entries AS (
  SELECT "organizationId" AS org_id, "createdByUserId" AS user_id, "createdAt" AS at, 'expense' AS kind
    FROM expenses WHERE "deletedAt" IS NULL
  UNION ALL
  SELECT "organizationId", "createdByUserId", "createdAt", 'income'
    FROM payments WHERE origin = 'CAPTURE' AND status = 'POSTED'
  UNION ALL
  SELECT "organizationId", "createdByUserId", "createdAt", 'income'
    FROM receivables WHERE origin = 'ADJUSTMENT' AND "deletedAt" IS NULL
)
SELECT p.code, o.name AS profile,
       count(e.at) FILTER (WHERE e.kind = 'income')  AS income,
       count(e.at) FILTER (WHERE e.kind = 'expense') AS expenses,
       count(e.at) FILTER (WHERE e.at > :'as_of'::timestamptz - interval '7 days') AS last_7_days,
       max(e.at)::date AS last_entry_on
FROM pilot p
JOIN memberships m ON m."userId" = p.id
JOIN organizations o ON o.id = m."organizationId"
LEFT JOIN entries e ON e.org_id = o.id AND e.at <= :'as_of'::timestamptz
GROUP BY p.code, o.id, o.name
ORDER BY p.code, o.name;

-- 2. One row per pilot user: activation and weekly use.
WITH pilot AS (
  SELECT u.id, 'P' || lpad(array_position(string_to_array(:'emails', ','), u.email)::text, 2, '0') AS code,
         COALESCE((SELECT min(t."acceptedAt") FROM terms_acceptances t WHERE t."userId" = u.id), u."createdAt") AS setup_at
  FROM users u
  WHERE u.email = ANY (string_to_array(:'emails', ','))
),
entries AS (
  SELECT "createdByUserId" AS user_id, "createdAt" AS at FROM expenses WHERE "deletedAt" IS NULL
  UNION ALL
  SELECT "createdByUserId", "createdAt" FROM payments WHERE origin = 'CAPTURE' AND status = 'POSTED'
  UNION ALL
  SELECT "createdByUserId", "createdAt" FROM receivables WHERE origin = 'ADJUSTMENT' AND "deletedAt" IS NULL
)
SELECT p.code,
       p.setup_at::date AS setup_on,
       min(e.at)::date AS first_entry_on,
       COALESCE(min(e.at) < p.setup_at + interval '7 days', false) AS activated,
       count(DISTINCT floor(extract(epoch FROM :'as_of'::timestamptz - e.at) / 604800))
         FILTER (WHERE e.at > :'as_of'::timestamptz - interval '28 days') AS weeks_with_entries_of_last_4,
       count(e.at) AS entries_total
FROM pilot p
LEFT JOIN entries e ON e.user_id = p.id AND e.at <= :'as_of'::timestamptz
GROUP BY p.id, p.code, p.setup_at
ORDER BY p.code;
```

Reading it:
- **Query 1** lists each pilot user's profiles with income and expense counts,
  the count in the last 7 days and the last entry date. It counts every entry
  in the profile, whoever logged it.
- **Query 2** is one row per pilot user, counting only what that person
  logged. `activated` is the activation bar. `weeks_with_entries_of_last_4`
  of 3 or 4 meets the weekly-use bar. The weeks are the four 7-day windows
  ending at `as_of`.

### 6b. Uptime checks and alerts (MUT-328)

**What it watches** (`infrastructure/terraform/monitoring.tf`, brief `.claude/designs/mut-328-uptime-alerts.md`):

| Watch | Rule | Severity |
|---|---|---|
| `GET /health`, `GET /ready`, portal `GET /` (must contain `id="root"`) | Each runs from all six Cloud Monitoring regions every 5 min. An alert fires when **2 or more regions fail on 2 rounds in a row** (about 6 min after the second failed round). It closes when the check passes again. One failed round, or one region failing, never alerts. | CRITICAL |
| Cloud SQL disk, on the instance the API serves from (`mutaba3a-pg`, `mutaba3a-pg2` after §6d) | Above 80% for 15 min | WARNING |
| Cloud SQL CPU, same instance | Above 90% for 15 min | WARNING |

Alerts go to email and SMS (Basel's call, 2026-10-19), plus any ids in `alert_notification_channels`. With no channel set, Terraform keeps only the checks and creates no alerts. Production ran that way until this section was applied.

**Cost:** the checks make about 160k runs a month, inside the 1M free per project. Channels are free. The 5 alert conditions cost about $0.50/month at most, if Google's per-condition alerting charge applies.

#### Apply (Basel, once)

1. Add two lines to the git-ignored `infrastructure/terraform/production.tfvars`. The phone number never goes in the repo:
   ```hcl
   alert_email      = "you@example.com"
   alert_sms_number = "+9725XXXXXXXX"   # E.164
   ```
   Leave `uptime_host` unset until the custom domain is live (MUT-112). Unset means the Cloud Run host.
2. Plan only the monitoring resources, so this is reviewed on its own and not inside a release:
   ```bash
   cd infrastructure/terraform
   terraform init -reconfigure -backend-config="bucket=$TF_STATE_BUCKET" -backend-config="prefix=mutaba3a-api/production"
   URL=$(terraform output -raw service_url)
   TAG=$(curl -fsS "$URL/health" | jq -r .version)   # the running image tag, so Cloud Run plans no change
   MON=(-target=google_monitoring_uptime_check_config.health -target=google_monitoring_uptime_check_config.endpoint
        -target=google_monitoring_notification_channel.email -target=google_monitoring_notification_channel.sms
        -target=google_monitoring_alert_policy.endpoint_down -target=google_monitoring_alert_policy.cloud_sql)
   terraform plan -var-file=production.tfvars -var image_tag="$TAG" "${MON[@]}"
   ```
   The first target is the check's *old* address: a targeted plan must name both sides of a `moved` block or Terraform refuses it ("Moved resource instances excluded by targeting"). Until this section is applied that same refusal stops `deploy.sh` step 0, so a release cannot go out before it (ADR-161). Expect `google_monitoring_uptime_check_config.health[0] has moved to …endpoint["health"]` with no change to it, then **`Plan: 9 to add, 0 to change, 0 to destroy`**: the `ready` and `portal` checks, 2 channels, 3 uptime policies and 2 Cloud SQL policies. The targets pull in the Cloud Run service and the attachments bucket as dependencies, so an unapplied change to either rides along: §6c's bucket `soft_delete_policy` 7 → 14 days showed here as `1 to change` on 2026-10-20 and was approved with it. Anything else marked change or destroy means stop and ask. In particular, a change to `google_cloud_run_v2_service.api` (the checks read its host, so `-target` plans it too) means main carries Terraform that isn't released yet: apply this with the next `make release server` instead. (If `alert_notification_channels` was already set, the old `/health` policy moves and shows one in-place change to its condition. That's expected.)
3. Apply the same command, with `apply` in place of `plan`. Any later `./scripts/deploy.sh` keeps these resources, because its full apply reads the same tfvars.
4. **Verify the SMS channel.** Cloud Monitoring sends nothing to an SMS channel until the code it texts is confirmed. Email needs no verification.
   ```bash
   CH=$(terraform output -raw alert_sms_channel)
   AUTH="Authorization: Bearer $(gcloud auth print-access-token)"
   curl -fsS -X POST -H "$AUTH" "https://monitoring.googleapis.com/v3/$CH:sendVerificationCode"
   curl -fsS -X POST -H "$AUTH" -H 'content-type: application/json' "https://monitoring.googleapis.com/v3/$CH:verify" -d '{"code":"G-123456"}'   # the code from the text
   ```
   Or use the console: Monitoring → Alerting → Edit notification channels → SMS → Verify. If your number's country isn't offered for SMS, the channel stays unverified and email still works.
5. **Check it's green.** After about 10 minutes, Monitoring → Uptime checks shows `mutaba3a-api /health`, `/ready` and `portal /` passing in every region. Monitoring → Alerting lists 5 policies, all with no open incidents.

#### Fire a test alert, then let it close (the drill)

There is no staging to scale to zero, so the drill adds a fourth check against a path that always fails. It goes through the same rule and the same channels, and production behaviour doesn't change. Pass it with `-var` only, never in tfvars, so the next `deploy.sh` removes it if you forget step 3.

1. **Fire.** `terraform apply -var-file=production.tfvars -var image_tag="$TAG" -var uptime_drill_path=/v1/uptime-drill "${MON[@]}"` adds 2 resources (the drill check and its policy). `/v1/uptime-drill` is a JSON 404. About 10 to 15 minutes later, an email and a text arrive: **"mutaba3a-api drill /v1/uptime-drill is down"**.
2. **Recover.** Run the same command with `-var uptime_drill_path=/health`. The check's path changes in place. Within about 10 minutes the incident closes and a closing notice arrives. *No closing notice?* The Google provider here (5.x) cannot set the policy's notification prompts, so the close notice depends on Cloud Monitoring's default (TD-185). Open each uptime policy in the console, turn on **Notify on incident closure**, and record that here. Terraform's updates leave that setting alone.
3. **Remove.** Run the same command without `uptime_drill_path`. It destroys the 2 drill resources. Write the date and how long each notice took into §7.

#### When an alert fires

- **`/health` down:** the service is down or unreachable. Check `gcloud run services describe mutaba3a-api --region=me-west1` (latest revision ready?) and the logs (§6). Roll back with `IMAGE_TAG=<old sha> ./scripts/deploy.sh` if a release caused it.
- **`/ready` down while `/health` is up:** the database. Check the `mutaba3a-pg` status in Cloud SQL (maintenance window: Sunday 03:00), and run `npm run db:psql`.
- **Portal down while `/health` is up:** the image shipped without `dist-hosted/`, or the domain (after MUT-112) points somewhere else. `curl -s "$URL/" | head` shows what is being served.
- **Cloud SQL disk or CPU:** not urgent. Query Insights in the console shows the heavy query. Disk grows by itself (`disk_autoresize`), and so does the bill.

#### When the domain moves (MUT-112)

Set `uptime_host` to the portal's bare hostname, or let MUT-326's domain input feed it (see `local.uptime_host` in `monitoring.tf`). Plan with the targets above. The checks may be replaced (new check ids) and the policies change to follow them. That's expected. Watch step 5 above again afterwards.

### 6c. Receipt files kept as long as the backups (TD-190)

Deleting a receipt deletes its object, and the database backups hold rows, not files. So the attachments bucket keeps a deleted object restorable (soft delete) for **14 days**, the same as the 14 daily Cloud SQL backups (`local.db_retained_backups` in `main.tf` sets both). A database restored to its oldest backup still finds every receipt's file. Restoring a file: pilot runbook §4.4.

Before this, the bucket had no explicit policy and kept GCS's default of 7 days.

**Cost:** a soft-deleted object bills at the bucket's STANDARD storage rate until it's purged, and restoring one is free. At pilot volumes (receipts are at most 10 MB) that's cents a month. Versioning with a non-current-version lifecycle rule would cost the same, but it also needs a rule to expire versions and a different restore command, so soft delete was chosen.

#### Apply (Basel, once)

The bucket change is in place: no object, the bucket's name and the API are untouched. The next `make release server` applies it anyway: deploy.sh's `terraform apply` shows it as one in-place change, and the release prints a reminder (`docs/operations/before-release.md`). To apply it before then, on its own, plan only the bucket:

```bash
cd infrastructure/terraform
terraform init -reconfigure -backend-config="bucket=$TF_STATE_BUCKET" -backend-config="prefix=mutaba3a-api/production"
TAG=$(curl -fsS "$(terraform output -raw service_url)/health" | jq -r .version)   # the running image tag
terraform plan -var-file=production.tfvars -var image_tag="$TAG" -target=google_storage_bucket.attachments
```

Expect **`Plan: 0 to add, 1 to change, 0 to destroy`**: `google_storage_bucket.attachments` updated in place, with `soft_delete_policy` `retention_duration_seconds = 604800 -> 1209600`. Anything else marked change, or any replace or destroy, means stop and ask. Then apply the same command with `apply` in place of `plan`.

Check it, record the date in INFRA.md §2, and delete the TD-190 line from `docs/operations/before-release.md`:

### 6d. Our own KMS key for the database and receipts (MUT-381, ADR-164)

The database and the attachments bucket move from Google's default encryption to our own Cloud KMS key, `mutaba3a-data`, in me-west1, rotated every 90 days. Cloud SQL can't add a key to an existing instance, so the API moves to a new instance, `mutaba3a-pg2`, filled from a fresh backup while the API is closed for a short window. `cmek_stage` in `production.tfvars` walks it: `off` (default) → `prepared` → `active`. **Only forward**: the key has `prevent_destroy`, and going back to `off` would plan its destroy.

Run every command from `server/` unless it says otherwise. `TAG` is the running image tag:

```bash
cd infrastructure/terraform
terraform init -reconfigure -backend-config="bucket=$TF_STATE_BUCKET" -backend-config="prefix=mutaba3a-api/production"
TAG=$(curl -fsS "$(terraform output -raw service_url)/health" | jq -r .version)
```

**Releases during this procedure.** The guard below is **off by default** until MUT-385 lands: while `cmek_stage` is `off` a release changes nothing, so releases run as they did before MUT-381. Turn it on with `SKIP_CMEK_GUARD=0` (every release, from every checkout) before step 1, and keep it on from then on (after the switch it is what stops a stale tfvars moving production back to mutaba3a-pg). With it on, `deploy.sh` refuses a release whose `production.tfvars` stage would move the database, and refuses while the service is closed (`lib/release-guard.sh`). So a release is fine before step 4 and after step 4.5 (the reopen), and is refused in between. It checks again before the migration and before the apply, minutes apart. The tfvars in *every* checkout you release from must say the same stage: git doesn't carry it.

#### Step 1: prepare (no downtime)

Set `cmek_stage = "prepared"` in `production.tfvars`, then:

```bash
terraform plan -var-file=production.tfvars -var image_tag="$TAG"
```

If the apply fails with a permission error on the key, the grants haven't propagated yet (IAM is eventually consistent): wait a minute and apply again.

Expect only additions: the KMS key ring and key, the Cloud SQL service identity, two key grants, `mutaba3a-pg2` with its database and user, and the KMS API. The bucket changes in place (its `encryption` block). The Cloud Run service and the DATABASE_URL secret must **not** change. Apply the same command with `apply`. The new instance takes about 10 minutes.

#### Step 2: the bucket (no downtime)

1. In the portal, attach a receipt to an expense and open it.
2. Check that the new object carries the key:

   ```bash

   ```

3. Rewrite the existing objects under the key, then open an old receipt in the portal:

   ```bash
   gcloud storage du -s "gs://$GCP_PROJECT_ID-mutaba3a-attachments"   # size first

   ```

4. Check nothing was missed (objects deleted or replaced while it ran make it error partway). This must print nothing; re-run the update for anything it lists:

#### Step 3: rehearse (no downtime)

```bash

scripts/cmek-cutover.sh rehearse --project $GCP_PROJECT_ID
```

It asks first, refuses if Cloud Run already serves from `mutaba3a-pg2`, copies a fresh backup into `mutaba3a-pg2`, checks the key survived the restore, and prints the timings and row counts. The total, plus about 15 s of drain and the two applies (a minute or two each), is the downtime to announce. Paste the table into pilot runbook §10. Tell Malafat's operator the window: its money calls fail while the API is closed.

#### Step 4: cut over (downtime: the API is closed)

In a quiet window. The `/health` and `/ready` uptime checks will page while the API is closed (§6b): expect it, or snooze those policies in Cloud Monitoring for the window. Run it from the checkout of the release that is live (`git checkout api-v<live>`), so the switch apply below changes nothing but the database (see "Expect" under 4.1).

```bash
scripts/cmek-cutover.sh cutover --project $GCP_PROJECT_ID
```

It pauses the nightly Stripe reconcile first, if the job exists and runs (§6e): Cloud Scheduler counts as internal traffic, so the job would still reach the closed API and write. Then it closes the API to outside traffic, waits 15 s for requests in flight, checks the close took, and records `mutaba3a-pg`'s write counters (rows inserted, updated, deleted). Then it copies again, compares every table's row count, re-reads the counters (any write since, an UPDATE included, stops it) and checks ingress is still closed. On any failure or mismatch it reopens the API on `mutaba3a-pg`, resumes the job it paused, and stops; nothing has moved. On success it leaves the API **closed** and the job paused, and prints the next steps:

1. The switch apply. Ingress stays closed:

   ```bash
   terraform apply -var-file=production.tfvars -var image_tag="$TAG" -var cmek_stage=active -var api_ingress=INGRESS_TRAFFIC_INTERNAL_ONLY
   ```

   **Expect** only: the DATABASE_URL secret version replaced, the Cloud Run service updated (its Cloud SQL volume), and the two Cloud SQL alert policies updated. Anything else (a new env var, a flag, a `moved` block) means this checkout isn't the live release: answer `no` and switch checkouts.
2. Check the serving revision mounts `mutaba3a-pg2`, the DATABASE_URL secret points at it, the key is set, and `mutaba3a-pg` took no write since the copy (pass the counters cutover printed):

   ```bash
   scripts/cmek-cutover.sh verify --project $GCP_PROJECT_ID --source-writes <inserted,updated,deleted from the cutover>
   ```

3. Take `mutaba3a-pg2`'s first backup of its own. Until it exists, its only backups are the nightly ones taken while it held rehearsal data, and point-in-time recovery has no base:

   ```bash
   gcloud sql backups create --instance=mutaba3a-pg2 --project=$GCP_PROJECT_ID --description="after the MUT-381 cutover"
   ```

4. Only now set `cmek_stage = "active"` in `production.tfvars` (and in every other checkout you release from).
5. Reopen:

   ```bash
   terraform apply -var-file=production.tfvars -var image_tag="$TAG" -var cmek_stage=active
   scripts/cmek-cutover.sh verify --project $GCP_PROJECT_ID   # now also /ready
   ```

6. Resume the Stripe reconcile, if cutover paused it (it prints this step only then). No apply resumes it, and `verify` warns while it's still paused:

   ```bash
   gcloud scheduler jobs resume mutaba3a-stripe-reconcile --location=me-west1 --project=$GCP_PROJECT_ID
   ```

### 6e. Stripe webhook and nightly reconcile (MUT-360)

Stripe tells the API about subscriptions through `POST /v1/billing/stripe/webhook`. A Cloud Scheduler job, `mutaba3a-stripe-reconcile`, POSTs to `/jobs/v1/billing/stripe-reconcile` at 03:30 Israel time and mirrors every subscription again, so a missed webhook is caught by morning. Each attempt gets 280 s (`attempt_deadline`, under Cloud Run's 300 s request timeout); the server stops its own run at about 200 s and lists `TIME_BUDGET` in its errors, and the next run (or a manual one) carries on. The route answers 200 with the run's summary, **502 `RECONCILE_FAILED`** when Stripe couldn't be listed at all (a bad or under-scoped key), and 409 `RECONCILE_RUNNING` when a run is already going. Anything but a 2xx is retried 3 times and pages (see "Alerts" below). Terraform (`infrastructure/terraform/main.tf`, brief `.claude/designs/mut-360-stripe-webhook.md` §2.7) holds:

| Resource | State until `stripe_enabled = true` |
|---|---|
| Secrets `mutaba3a-api-stripe-secret-key` and `mutaba3a-api-stripe-webhook-secret`, readable by the API's service account | Exist, empty. Terraform never writes their values: you add them with `gcloud`. Not mounted, so the Stripe routes answer 503 |
| Secret `mutaba3a-api-job-token`, generated by Terraform (`random_password.job_token`) | Mounted as `MUTABA3A_JOB_TOKEN` on every release. Opens `/jobs/*` only, never `/admin/*` |
| The Scheduler job, and `cloudscheduler.googleapis.com` | The API is enabled; the job doesn't exist |
| 3 log-match alert policies (`monitoring.tf`, `google_monitoring_alert_policy.stripe`), on the §6b channels | Don't exist. Created with the job, only if an alert channel is set |

**Cost:** 3 Scheduler jobs per billing account are free and this is the only one. The 3 secrets cost about $0.18/month.

#### Business email and the signup review queue (MUT-367, ADR-178)

**The screen.** Every signup address is screened before any link is mailed:
- Disposable addresses and domains that take no mail are refused (400 `EMAIL_NOT_ACCEPTED`).
- Webmail and relay addresses wait for you.
- Any other domain is checked by DNS and RDAP, in 2 s, cached 24 h:
  - it signs up at once with an MX, a resolving apex or www, and a registration at least 90 days old;
  - otherwise it waits, with the reasons recorded.
- A waiting account is `PENDING_REVIEW`. It has no trial yet, can't sign in (the portal shows the waiting screen), and can recover its password.

| Piece | Where | Production |
|---|---|---|
| `EMAIL_DOMAIN_CHECKER` | config (no Terraform variable) | `dns`, the default; the server refuses `fixture` in production. It needs outbound DNS and HTTPS to `data.iana.org` and the registries' RDAP servers (the same egress the FX rates use) |
| `OPERATOR_ALERT_EMAIL` | var `operator_alert_email` (`infrastructure/terraform/email.tf`) | The digest's recipient. Unset = no digest (boot warns). At most one mail per UTC hour, only when new signups wait |
| Lists | `server/src/email/domains/{disposable,free-webmail,relay}.txt` | Shipped in the image. Refresh the disposable list: `npm --prefix server run email-domains:update -- --commit <sha>` (CC0, pinned commit), review, commit, release |

**Deciding** (MUTABA3A_ADMIN_TOKEN in the environment, `--url` = the API):
```bash
npm --prefix server run signups:review                               # who waits, since when, and why (webmail, rdap-age-12d …)
npm --prefix server run signups:review -- --approve rana@gmail.com   # opens it, starts the 14-day trial, mails "your account is ready"
npm --prefix server run signups:review -- --decline rana@gmail.com   # deletes the empty account, mails "we couldn't open it" with MAIL_REPLY_TO
```
- A decline keeps the review row with no person and logs `user.signup_declined`; the address may sign up again.
- A decline is refused (409 `NOT_EMPTY`) if the account holds anything else, such as a grant.
- `enable:user` / `disable:user` refuse a waiting account; decide it instead.
- Moving a webmail provider to instant signup is a recorded decision plus an edit to `free-webmail.txt`, not code.

### 6g. Closing accounts and the hourly hard delete (MUT-333, ADR-188)

A person closes their own account from the portal's You › Account (`POST /v1/me/closure`, the password again). The account is then **closing** for 30 days: it signs in only to keep it (`DELETE /v1/me/closure`) or sign out, and every other request answers 403 `ACCOUNT_CLOSING`. After that it no longer signs in, and the hourly job deletes it.

| Piece | Where | State |
|---|---|---|
| Scheduler job `mutaba3a-account-purge` | `infrastructure/terraform/main.tf`, hourly at :15 (Asia/Jerusalem), `POST /jobs/v1/accounts/purge` with the job token | Always on: closing is a promise in the privacy policy |
| Alerts "Account deletion needs the operator" and "Account deletion job failed" | `monitoring.tf` (`account_purge`), on the §6b channels | Created with the alert channels |
| Operator run | `npm --prefix server run accounts:purge -- --url "$URL" [--dry-run]` (`POST /admin/v1/accounts/purge`) | Any time; `--dry-run` changes nothing |
| Stripe | the restricted key needs **Write on Subscriptions** (close ends subscriptions) and Write on Customers (the purge deletes customers) | Edit the key in place (Developers › API keys › the key › Edit); its secret doesn't change |

**What a run does,** for at most 25 due accounts and about 200 s: claims the account (from then on it can't be kept), deletes every Stripe customer whose metadata names the person, then in one transaction deletes the profiles they alone own with every row, passes a Business profile they share to a co-owner, anonymizes their records on other profiles, clears audit details naming them (the bare id stays as the tombstone), deletes their own rows and the user, and queues the deleted profiles' bucket prefixes; it empties those after the commit (and any left queued at the start of each run). The bucket's soft delete keeps the files 14 days more, like the backups.

**When the alert fires:** run the dry run; `stripe-failed` is transient (the next hour retries, the account stays claimed), `stripe-unavailable` means Stripe isn't configured while the person has a customer, `error` names the exception in the log, `storage` is a bucket problem (the prefix stays queued). Fix it and run without `--dry-run`, or let the next hour do it.

### Open: production probably has the original M7 enum (MUT-59, fix ready)

M8 edited the M7 migration in place (D20). `acb1144` created
`FeeProposalStatus` as `('PROPOSED', 'CLIENT_APPROVED', 'AGREED', 'CONVERTED', 'WITHDRAWN')`
and the columns `agreedOn` and `agreedNote`. `main` now creates
`('PROPOSED', 'APPROVED', 'WITHDRAWN')` without them.

Revision `00003` rolled `acb1144`, and `deploy.sh` migrates before it rolls, so
production recorded the original M7. `prisma migrate deploy` never re-runs a
recorded migration. The database therefore still has the old enum while the
service writes `APPROVED`.

What breaks:

- **Approving a fee proposal** fails with a Postgres enum error, which
  reaches Partners as a 500. Malafat `web@2.2.4` offers the button.
- **Reading a proposal in a removed status** fails too.

**Until the fix is deployed, nobody approves a proposal.**

**The fix** is the migration `20261011120000_mut59_fee_proposal_enum_repair`
(MUT-59). It ships with the next `./scripts/deploy.sh` from `main`, in step 4,
before the service rolls. It runs as one statement, so it either does all of
the following or nothing:

- **Refuses** if a `CONVERTED` proposal has no agreement, or if a project would
  be left with two open proposals. The error names the rows.
- **Audits first:** every touched row gets a `SYSTEM` audit event
  `fee_proposal.repaired` holding its previous values. That covers status,
  approval date and note, agreed amount, `agreedOn` and `agreedNote`.
- **Maps the statuses:**
  - `CONVERTED` → `APPROVED`, with the approval date and amount taken from
    M7's fields or else the agreement;
  - `CLIENT_APPROVED` and `AGREED` → `PROPOSED`, i.e. still open, and the
    Partner approves them again in M8, which creates the agreement.
- **Reshapes the schema:** recreates the enum with three values and drops
  `agreedOn` and `agreedNote`.

On a database that already has M8's shape it does nothing.

1. The service was not rolled, and nothing was changed.
2. Fix the named rows in `npm run db:psql`. For example, withdraw a

   `UPDATE fee_proposals SET status = 'WITHDRAWN', "withdrawnReason" = '…' WHERE id = '…'`.

4. Re-run `./scripts/deploy.sh`.
