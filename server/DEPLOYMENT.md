# Mutaba3a API — deployment runbook (Money v1, Milestone 1)

Operator steps to take the hosted API from "code on main" to "a Partner can
connect from Malafat". Everything here is run by a person; nothing in either
repository deploys itself (ADR-025 §9, Malafat rule 11).

Time budget for a first environment: about 45 minutes, of which Cloud SQL
creation is 10–15 minutes of waiting.

## 0. What you are deploying

| Piece | Name (production / staging) | Defined in |
|---|---|---|
| Cloud Run service | `mutaba3a-api` / `mutaba3a-api-staging` | `infrastructure/terraform/main.tf` |
| Cloud Run job (migrations) | `mutaba3a-api-migrate` / `-staging` | same |
| Cloud SQL Postgres 16 | `mutaba3a-pg` / `mutaba3a-pg-staging`, db `mutaba3a`, user `mutaba3a_api` | same |
| Secrets | `mutaba3a-api-database-url[-staging]`, `mutaba3a-api-admin-token[-staging]` | same (values generated by Terraform) |
| Service account | `mutaba3a-api[-staging]@<project>.iam` — `cloudsql.client` + accessor on its two secrets only | same |
| Artifact Registry | `<region>-docker.pkg.dev/<project>/mutaba3a/mutaba3a-api[-migrate]:<sha>` | same; images built by `cloudbuild.yaml` |
| Uptime check | `GET /health` every 5 min; alert only if you pass notification channels | same |

Staging issues and accepts **`test`** API keys, production **`live`** keys. A
key can never work against the other environment (`config.API_KEY_ENVIRONMENT`).

`scripts/deploy.sh` is the only command you need per rollout. It builds both
images, points the migration job at the new image, runs `prisma migrate deploy`,
rolls the service, and runs `scripts/smoke.ts`. The service stays on the old
revision if the migration fails.

Both environments run **one instance** (`max_instances = 1`, validated in
Terraform) until TD-017 lands a shared rate-limit store. That is deliberate.

## 1. One-time prerequisites

### 1.1 Decide the GCP project

Two valid choices. Pick one and write it down in `.claude/INFRA.md`:

- **Dedicated project** (recommended, e.g. `mutaba3a-prod`): clean ownership and
  billing for a product that will serve customers other than Malafat (ADR-024).
- **Malafat's project** (`malafat-production`): fewer moving parts; every
  resource name is prefixed `mutaba3a-` so nothing collides.

Either way the region is **`me-west1`** so firm data stays beside the CRM
(ADR-024 residency guarantee). Billing must be enabled on the project.

### 1.2 Tools on your workstation

```bash
gcloud --version        # Google Cloud SDK
terraform version       # >= 1.5
node --version          # 22.x
git --version
```

Authenticate once; Terraform uses the application-default credential:

```bash
gcloud auth login
gcloud auth application-default login
gcloud config set project <PROJECT_ID>
```

Your account needs **Owner** on the project, or all of: `run.admin`,
`cloudsql.admin`, `secretmanager.admin`, `artifactregistry.admin`,
`iam.serviceAccountAdmin`, `iam.serviceAccountUser`,
`resourcemanager.projectIamAdmin`, `serviceusage.serviceUsageAdmin`,
`cloudbuild.builds.editor`, `monitoring.editor`, `storage.admin`.

### 1.3 Terraform state bucket

State holds the generated database password and admin token. Keep the bucket
private to operators, versioned, in-region:

```bash
gsutil mb -p <PROJECT_ID> -l me-west1 -b on gs://<PROJECT_ID>-terraform-state
gsutil versioning set on gs://<PROJECT_ID>-terraform-state
```

### 1.4 Environment files (git-ignored)

```bash
cd server/infrastructure/terraform
cp staging.tfvars.example staging.tfvars          # set project_id
cp production.tfvars.example production.tfvars    # set project_id; add alert channels later
```

Nothing secret goes in these files; Terraform generates the DB password and
the admin token itself.

### 1.5 Cloud Build can push images

Cloud Build runs as the project's Compute Engine default service account in new
projects. If the first build fails with a permission error on Artifact Registry
or Cloud Logging, grant it once:

```bash
PROJECT_NUMBER=$(gcloud projects describe <PROJECT_ID> --format='value(projectNumber)')
gcloud projects add-iam-policy-binding <PROJECT_ID> \
  --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
  --role="roles/artifactregistry.writer"
gcloud projects add-iam-policy-binding <PROJECT_ID> \
  --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
  --role="roles/logging.logWriter"
```

(Or build locally instead: `BUILD_MODE=local ./scripts/deploy.sh …` uses your
Docker daemon and pushes with your own credentials.)

## 2. Deploy staging

From a clean checkout of `main` (the script refuses uncommitted changes in
`server/`, so the image tag always names a commit):

```bash
cd server
npm ci
export GCP_PROJECT_ID=<PROJECT_ID>
export TF_STATE_BUCKET=<PROJECT_ID>-terraform-state
./scripts/deploy.sh staging
```

What you will see, and what to answer:

1. `terraform init` against `gs://…/mutaba3a-api/staging`.
2. A targeted plan that creates only the Artifact Registry repository → **yes**.
3. Cloud Build builds `mutaba3a-api:<sha>` and `mutaba3a-api-migrate:<sha>` (3–5 min).
4. A targeted plan for the migration job. Because the job depends on them, this
   plan also creates the Cloud SQL instance, database, user, both secrets, the
   service account and its IAM → **yes**. Cloud SQL takes 10–15 minutes.
5. The job runs `prisma migrate deploy` and the script waits. Output ends with
   `All migrations have been successfully applied`.
6. The full plan: Cloud Run service, public invoker, uptime check → **yes**.
7. `smoke.ts` runs the unauthenticated checks and prints `smoke: all checks passed`.
8. The last line is the service URL. Keep it: `https://mutaba3a-api-staging-….a.run.app`.

Repeat runs are the same command; plans 2 and 4 will show no changes and the
service rolls to the new tag. Pass `AUTO_APPROVE=1` once you trust it.

## 3. Prove staging works

Read the generated operator token (it never appears in logs or the repo):

```bash
export MUTABA3A_ADMIN_TOKEN=$(gcloud secrets versions access latest \
  --secret=mutaba3a-api-admin-token-staging --project=$GCP_PROJECT_ID)
```

Run the full smoke test. With the token set it also provisions a throwaway
organization, issues a key, validates it on `GET /v1/integration`, revokes it
and proves the revoked key is rejected — the Milestone 1 exit criterion
against a real deployment:

```bash
URL=$(cd infrastructure/terraform && terraform output -raw service_url)
npm run smoke -- --url "$URL"
```

Expected: every line `PASS`, ending in `smoke: all checks passed`. The
`smoke-<stamp>` organization stays (organizations are never deleted; audit
retention). Also confirm the uptime check turned green in Cloud Monitoring
after ~5 minutes.

## 4. Provision the first firm

Keys are operator-issued until Mutaba3a has accounts (TD-018). The secret is
printed **once**; hand it to the Partner over a secure channel, never by email
or chat.

```bash
npm run provision -- --url "$URL" \
  --name "Sader Law Firm" --currency ILS --timezone Asia/Jerusalem --key-name "Malafat"
```

Output: `organization sader-law-firm = <uuid>` and the key
`mut_test_<prefix>_<secret>` (on production: `mut_live_…`). The key carries
every scope Malafat needs; `GET /v1/integration` will report `missingScopes: []`.

To issue a second key later (rotation is also possible from Malafat's settings
page): `npm run provision -- --url "$URL" --organization-id <uuid> --key-name "Malafat (rotated)"`.

## 5. Wire Malafat to it

In the Malafat repository (`web/crm-platform`), the release contract now mounts
`MUTABA3A_API_URL` from a secret. Create it **before** the next web release or
`pnpm release` fails at `gcloud run deploy` (loudly; the old revision keeps serving):

```bash
printf %s "$URL" | gcloud secrets create malafat-web-mutaba3a-api-url \
  --project=malafat-production --data-file=- \
  --replication-policy=user-managed --locations=me-west1
```

Then release web as usual (`pnpm release`), run the tenant migration step
already listed in `scripts/release-steps.ts` (`pnpm db:update_tenants --with-proxy`,
creates `money_integrations`), and in the firm's Malafat as a Partner:
**Settings › Money & Mutaba3a › Connect**, paste the key. The page shows the
organization name, masked key and scopes, and "Test connection" calls
`GET /v1/integration` round-trip.

Caveat: Malafat's `malafat-web-*` secrets are shared by its staging and
production services. While only Mutaba3a staging exists, the secret holds the
staging URL and firms get `test` keys; once production exists (step 6), add a
new secret version with the production URL and re-issue `live` keys. Pointing
production Malafat at Mutaba3a staging is acceptable for a pilot and nothing
else.

## 6. Deploy production

Same command, different environment. `production.tfvars` turns on REGIONAL
availability, backups with point-in-time recovery, deletion protection and
`min_instances = 1` (no cold start on the first request of the day):

```bash
./scripts/deploy.sh production
export MUTABA3A_ADMIN_TOKEN=$(gcloud secrets versions access latest \
  --secret=mutaba3a-api-admin-token --project=$GCP_PROJECT_ID)
URL=$(cd infrastructure/terraform && terraform output -raw service_url)
npm run smoke -- --url "$URL"
npm run provision -- --url "$URL" --name "Sader Law Firm" --currency ILS --timezone Asia/Jerusalem
printf %s "$URL" | gcloud secrets versions add malafat-web-mutaba3a-api-url --project=malafat-production --data-file=-
```

Then release Malafat web once more so the new secret version is mounted, and
connect with the `live` key.

Optional: put `api.mutaba3a.app` in front of the run.app URL. Cloud Run domain
mappings are not offered in `me-west1`, so this is a Cloudflare proxied CNAME
(the same approach as `malafat-router`) or an external HTTPS load balancer. Not
required for M1; the run.app URL is stable for the life of the service.

## 7. Day-2 operations

| Task | Command |
|---|---|
| Roll a new commit | `./scripts/deploy.sh production` (from `main`) |
| Roll back the service | `IMAGE_TAG=<old sha> ./scripts/deploy.sh production` — migrations are forward-only; a rollback that needs a schema revert is a new migration |
| Logs | `gcloud run services logs read mutaba3a-api --region=me-west1 --limit=200` (pino JSON; `requestId` matches the error envelope Malafat shows) |
| Migration job history | `gcloud run jobs executions list --job=mutaba3a-api-migrate --region=me-west1` |
| Rotate the admin token | `cd infrastructure/terraform && terraform apply -var-file=production.tfvars -var image_tag=<current sha> -replace=random_password.admin_token`, then `./scripts/deploy.sh production` so the new revision reads the new version |
| Rotate the DB password | same with `-replace=random_password.db` (Cloud SQL user and the URL secret update together), then redeploy |
| Revoke a firm's key | `curl -X POST "$URL/admin/v1/api-keys/<id>/revoke" -H "x-admin-token: $MUTABA3A_ADMIN_TOKEN" -H 'content-type: application/json' -d '{"reason":"…"}'`; key ids are on `GET /admin/v1/organizations/<id>` |
| Audit trail of a firm | `GET /admin/v1/organizations/<id>/audit` with the admin token |
| Connect psql | `cloud-sql-proxy <connection name> --port 5440` then `psql "$(gcloud secrets versions access latest --secret=mutaba3a-api-database-url)"` with `host=` swapped for `localhost:5440` |
| Backups | Cloud SQL automated daily at 03:00 + PITR 7 days (production); on-demand: `gcloud sql backups create --instance=mutaba3a-pg` |
| Scale beyond one instance | blocked by Terraform validation until TD-017; do not raise `max_instances` by hand |
| Tear down staging | `terraform destroy -var-file=staging.tfvars -var image_tag=x` (deletion protection is off for staging only) |

CI (`.github/workflows/server-ci.yml`) runs type-check, lint, unit + route
tests, the Postgres contract suite, the OpenAPI drift check, both Docker
builds with a `/health` probe of the runtime image, and `terraform validate`
on every change under `server/`. A red `Server CI` means do not deploy.

## 9. Where to go from here

1. **Deploy staging and run the full smoke test** (§2–3). Until this happens,
   M1's last acceptance criterion ("works against a real test MUT environment")
   is unmet on both sides.
2. **Pilot one firm on staging** (§4–5): Sader Law Firm connects with a `test`
   key, exercises connect / test / rotate / disconnect from Malafat's Money
   settings page. This is the only end-to-end proof of ADR-150's error mapping.
3. **Production** (§6) once the pilot has survived a week.
4. **Then M2** — customers and projects (`money-v1-api-contract.md` §3 M2):
   the first financial resources, Malafat's client/matter → customer/project
   mapping, and the first real ledger tables. Prerequisites that are now in
   place: CI, a migration job, a contract drift gate, and an environment to
   test against.
5. In parallel, two product decisions that block nothing in M2 but shape M3+:
   TD-018 (self-serve provisioning vs operator-issued keys) and MAL-870
   (add-on entitlement and OAuth money scopes).
