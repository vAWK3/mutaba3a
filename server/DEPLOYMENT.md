# Mutaba3a API — deployment runbook (Money v1 and the hosted portal)

Operator steps to take the hosted API from "code on main" to "a Partner can
connect from Malafat". Everything here runs on your machine, the way Malafat's
`pnpm release` does: Docker builds locally, migrations run locally through the
Cloud SQL Auth Proxy, Terraform applies from your shell. GCP only hosts the
result: one Cloud Run service, one Cloud SQL instance, a private attachments
bucket and three secrets. There is
no staging environment for now and nothing builds or migrates inside GCP
(ADR-026).

Time budget for the first deploy: about 40 minutes, of which Cloud SQL
creation is 10–15 minutes of waiting.

## 0. What you are deploying

| Piece | Name | Defined in |
|---|---|---|
| Cloud Run service | `mutaba3a-api` (min 1, max 1 instance) | `infrastructure/terraform/main.tf` |
| Cloud SQL Postgres 16 | `mutaba3a-pg`, db `mutaba3a`, user `mutaba3a_api`, REGIONAL, daily backups + PITR | same |
| Secrets | `mutaba3a-api-database-url`, `mutaba3a-api-admin-token`, `mutaba3a-api-session-pepper` (MUT-38) — values generated by Terraform | same |
| Attachments bucket | `<project>-mutaba3a-attachments`, private; M6 attachments and MUT-42 expense receipts (`org/{id}/expense-receipts/…`) | same |
| Service account | `mutaba3a-api@<project>.iam` — `cloudsql.client`, accessor on its three secrets, object access on the bucket | same |
| Artifact Registry | `me-west1-docker.pkg.dev/<project>/mutaba3a/mutaba3a-api:<sha>` | same; image built by `scripts/deploy.sh` on your machine |
| Uptime check | `GET /health` every 5 min; alert only if you pass notification channels | same |
| Hosted portal | `dist-hosted/` (MUT-45), baked into the same image at `/app/portal`, served by the same Cloud Run service — no separate domain, load balancer or Terraform resource | `Dockerfile`, `src/app.ts` |

The service issues and accepts **`live`** API keys (`config.API_KEY_ENVIRONMENT`).

`scripts/deploy.sh` is the only command per rollout. It builds the hosted
portal (`npm run build:hosted` at the repo root) and copies it into the Docker
context, builds the image with your Docker daemon, pushes it, runs `prisma
migrate deploy` from `server/` through the Cloud SQL Auth Proxy, applies
Terraform with the new tag, and runs `scripts/smoke.ts` against the API and
the portal both. If the migration fails the service is not touched.

The service runs **one instance** (`max_instances = 1`, validated in
Terraform) until TD-017 lands a shared rate-limit store. That is deliberate.

## 1. One-time prerequisites

### 1.1 Decide the GCP project

Two valid choices. Pick one and record it in `.claude/INFRA.md` (the first
production run on 2026-10-08 chose **`malafat-production`**; the resources
below exist there now):

- **Dedicated project** (recommended, e.g. `mutaba3a-prod`): clean ownership
  and billing for a product that will serve customers other than Malafat
  (ADR-024).
- **Malafat's project** (`malafat-production`): fewer moving parts; every
  resource name is prefixed `mutaba3a-` so nothing collides.

Either way the region is **`me-west1`** so firm data stays beside the CRM
(ADR-024 residency guarantee). Billing must be enabled on the project.

### 1.2 Tools on your machine

```bash
gcloud --version          # Google Cloud SDK
docker info               # Docker Desktop, daemon running
cloud-sql-proxy --version # brew install cloud-sql-proxy   (v2)
terraform version         # >= 1.5                          (brew install terraform)
node --version            # 22.x
```

Authenticate once; Terraform and the proxy use the application-default
credential, Docker pushes with your gcloud identity:

gcloud auth login

gcloud config set project <PROJECT_ID>
gcloud auth configure-docker me-west1-docker.pkg.dev

Your account needs **Owner** on the project, or all of: `run.admin`,
`cloudsql.admin`, `cloudsql.client`, `secretmanager.admin`,
`artifactregistry.admin`, `iam.serviceAccountAdmin`, `iam.serviceAccountUser`,
`resourcemanager.projectIamAdmin`, `serviceusage.serviceUsageAdmin`,
`monitoring.editor`, `storage.admin`.

### 1.5 Sentry error reporting (one-time, ADR-091, MUT-147)

Separate from the GCP rollout: `server/infrastructure/sentry/` has its own
state, and `deploy.sh` never touches it. The rules are in
`docs/observability/README.md`.

1. **Org.** Sign in to Sentry and create a **new organization in the EU
   (Frankfurt) region**, slug `mutaba3a` (the product, so no other product is
   added to it by habit). The region can't be changed later. Don't reuse another
   product's org. Turn on **two-factor authentication on your own account first**:
   step 5 makes the org require it, and Sentry refuses that setting from an
   account without 2FA.
2. **Plan and budget.** Stay on the **Developer (free)** plan. Under
   Settings › Subscription, set the **pay-as-you-go budget to $0**, so overage
   is dropped and never billed, and keep Sentry's **quota notification emails**
   on. Check the plan's current monthly error quota on Sentry's pricing page; if
   it isn't 5,000, set `monthly_event_quota` in `production.tfvars` to match.
3. **Two tokens, two names** (D8).
   - **Admin token**, `SENTRY_ADMIN_TOKEN`: a **personal (user) auth token**
     (`sntryu_…`) created on your 2FA-enabled account, with `org:write`,
     `project:admin`, `team:admin` and `alerts:write`. An org auth token
     (`sntrys_…`) can't carry those scopes, and `require2FA` needs a user with
     2FA. Hand it to each command below. Never `export SENTRY_AUTH_TOKEN` with it: that name
     belongs to the upload token, and build tooling reads it.
   - **Upload token**, `SENTRY_AUTH_TOKEN`: an org auth token (`sntrys_…`) with
     release and upload scopes only, for MUT-149..151 builds.

   Store neither in the repo, a tfvars file or the Flutter `.env`.
4. **Apply the projects, keys, alerts and spike protection:**

   ```bash
   cd server/infrastructure/sentry
   cp production.tfvars.example production.tfvars    # set organization (= the SENTRY_ORG in step 5) and the origins
   read -rs SENTRY_ADMIN_TOKEN                       # paste the admin token; it isn't echoed or exported
   terraform init -backend-config="bucket=$TF_STATE_BUCKET" -backend-config="prefix=mutaba3a-sentry/production"
   SENTRY_AUTH_TOKEN="$SENTRY_ADMIN_TOKEN" terraform plan -var-file=production.tfvars
   SENTRY_AUTH_TOKEN="$SENTRY_ADMIN_TOKEN" terraform apply -var-file=production.tfvars
   ```

   The personal token reaches every org you belong to, and the step 5 guard runs
   after this apply. So before applying, read the org slug in the plan: every
   resource should show `organization = "mutaba3a"`.

   If the plan errors on `de.sentry.io`, or the apply stops on the "not in the
   EU region" postcondition, **stop and check the org's data region** in its
   settings. Never retry against `sentry.io`: that would hide an org created in
   the US (D5).
5. **Apply the org privacy settings.** The Terraform provider can't hold them,
   so this script sets them and reads them back. Before writing anything it
   refuses an org outside the EU region, and an org holding any project that
   isn't `mutaba3a-…`, which catches a mistyped `SENTRY_ORG`. Run it from the
   repo root:

   ```bash
   cd "$(git rev-parse --show-toplevel)"
   SENTRY_ADMIN_TOKEN="$SENTRY_ADMIN_TOKEN" SENTRY_ORG=mutaba3a npx tsx scripts/sentry-org-settings.ts --apply
   ```

   It prints the target org and host, then exits 1 and lists any setting that
   didn't stick. Re-run with `--check` whenever you want to confirm nobody
   changed them in the UI. Sensitive fields you add by hand are kept.
6. **Copy each DSN to its home** (the table in `docs/observability/README.md`):

   ```bash
   terraform -chdir=server/infrastructure/sentry output -json dsn
   ```

   Nothing reads the DSNs until MUT-148..151 wire the SDKs. Then
   `unset SENTRY_ADMIN_TOKEN`.
7. **Read back.** In Sentry, confirm:
   - four projects, each with one key, capped per day;
   - spike protection on;
   - three alerts per project;
   - the portal and landing projects' Allowed Domains.

   Then update INFRA's "Error reporting" Status row with the date.

A new portal or landing origin (the custom domain, MUT-112) goes into
`portal_origins` / `landing_origins` followed by `terraform apply`. Until
then, that origin's errors are dropped.

## 2. Deploy

From a clean checkout of `main` (the script refuses uncommitted changes in
`server/`, so the image tag always names a commit):

```bash
cd server
npm ci
export GCP_PROJECT_ID=<PROJECT_ID>
export TF_STATE_BUCKET=<PROJECT_ID>-terraform-state
./scripts/deploy.sh
```

What you will see, and what to answer:

1. `terraform init` against `gs://…/mutaba3a-api/production`.
2. A targeted plan that creates the Artifact Registry repository, the Cloud SQL
   instance, database and user, and the database-URL secret → **yes**.
   Cloud SQL takes 10–15 minutes (about 5 on a quiet day). The two warnings
   `Resource targeting is in effect` / `Applied changes may be incomplete` are
   expected here: this first apply is deliberately partial because the image
   has to be pushed and the database migrated before the service can start.
   Step 5 is the complete apply.
3. `docker build --platform linux/amd64` on your machine, then `docker push`
   of `mutaba3a-api:<sha>` (first build 2–4 min; later builds are cached).
4. `cloud-sql-proxy` starts on `127.0.0.1:5440`, `prisma migrate deploy` runs
   from `server/` against production, output ends with
   `All migrations have been successfully applied`, the proxy stops.
5. The full plan: service account + IAM, admin-token secret, Cloud Run
   service, public invoker, uptime check → **yes**.
6. `smoke.ts` runs the unauthenticated checks and prints `smoke: all checks passed`.
7. The proxy starts again and `npm run post-roll` repairs rows the old revision
   wrote after the migration (MUT-61: a person's payment must be `origin
   CAPTURE`) and gives any user without one a personal profile (MUT-120
   shipped with no backfill). Normally prints `post-roll: 0 captured payment(s)
   re-marked origin CAPTURE` and `post-roll: 0 personal profile(s) backfilled,
   0 skipped`; the proxy stops. A `still has no personal profile` warning names
   a user to provision by hand.
8. The last line is the service URL: `https://mutaba3a-api-….a.run.app`. Keep it.

Repeat runs are the same command; plan 2 shows no changes and the service
rolls to the new tag. Pass `AUTO_APPROVE=1` once you trust it.

### 2.1 If a step fails

The script stops at the first error (`set -e`) and prints `[deploy] …` in red.
Nothing it has already created is lost, and **re-running `./scripts/deploy.sh`
is always the recovery**: Terraform reconciles only what is missing, Docker
reuses the cached layers, the registry already holds the tag, and
`prisma migrate deploy` finds `No pending migrations`. Do not run `terraform
destroy` or delete resources by hand to "start clean"; the Cloud SQL instance
has deletion protection and a fresh one costs another 10 minutes.

| Where it stopped | What exists | What to do |
|---|---|---|
| Step 2 (Cloud SQL) | possibly a half-created instance | wait a minute, re-run; Terraform picks the instance up from state |
| Step 3 (docker) | nothing new | fix Docker (daemon, auth: `gcloud auth configure-docker me-west1-docker.pkg.dev`), re-run |
| Step 4 (migration) | image pushed, database untouched or partially migrated | read the Prisma error; the service was **not** rolled. Fix the migration, commit, re-run |
| Step 5 (full apply) errors on `google_cloud_run_v2_service.api` | database migrated, secrets and service account created, **no service** | fix the Terraform error (below), re-run. `terraform output service_url` does not exist until this step succeeds, so §3 cannot run yet |
| Step 6 (smoke) | everything, service URL printed | the service is up but a check failed; read the `FAIL` line, see §6 for logs |

The failure the first production run hit on 2026-10-08 was step 5:

```
Error 400: template.containers[0].env: The following reserved env names were
provided: PORT. These values are automatically set by the system.
```

Cloud Run sets `PORT` to the declared `container_port` (8787) itself and
refuses a template that also lists it. The `PORT` env entry was removed from
`main.tf` in the fix that accompanies this note; the service reads the
injected value through `config.PORT`. If you see this error you are on an
older commit: pull `main` and re-run.

After a step-5 failure the symptoms downstream are: `terraform output -raw
service_url` says `Output "service_url" not found`, and if you then run
`npm run smoke -- --url "$URL"` with that empty `URL`, the smoke script exits
with code 2 and `--url is empty …` (older builds crashed with
`Failed to parse URL from /health`, which meant the same thing).

## 3. Prove it works

Read the generated operator token (it never appears in logs or the repo):

```bash
export MUTABA3A_ADMIN_TOKEN=$(gcloud secrets versions access latest \
  --secret=mutaba3a-api-admin-token --project=$GCP_PROJECT_ID)
```

Run the full smoke test. With the token set it also provisions a throwaway
organization, issues a key, validates it on `GET /v1/integration`, revokes it
and proves the revoked key is rejected — the Milestone 1 exit criterion
against the real deployment:

```bash
URL=$(cd infrastructure/terraform && terraform output -raw service_url) || exit 1
echo "$URL"        # https://mutaba3a-api-….a.run.app — if this is empty, §2 did not finish; see §2.1
npm run smoke -- --url "$URL"
```

Expected: every line `PASS`, ending in `smoke: all checks passed`. The
`smoke-<stamp>` organization stays (organizations are never deleted; audit
retention). Also confirm the uptime check turned green in Cloud Monitoring
after ~5 minutes.

## 4. Provision the first firm

Keys are operator-issued (TD-018, Accepted). The secret is
printed **once**; hand it to the Partner over a secure channel, never by email
or chat.

```bash
npm run provision -- --url "$URL" \
  --name "Sader Law Firm" --currency ILS --timezone Asia/Jerusalem --key-name "Malafat"
```

Output: `organization sader-law-firm = <uuid>` and the key
`mut_live_<prefix>_<secret>`. The key carries every scope Malafat needs;
`GET /v1/integration` will report `missingScopes: []`.

To issue a second key later (rotation is also possible from Malafat's settings
page): `npm run provision -- --url "$URL" --organization-id <uuid> --key-name "Malafat (rotated)"`.

### 4a. Refresh Malafat's vendored contract

Malafat vendors a copy of this API's contract. A test fails when its client
calls a path, method or field the copy lacks. Refresh it from the deployed
`main` commit, never from a feature branch, so the file names a commit that
exists on the remote. Do it whenever a deploy changes `openapi/openapi.yaml`.

```bash
cd server
npm run -s openapi:json > /path/to/crm-platform/apps/web/src/features/money/contract/mutaba3a-openapi.json
node -e "JSON.parse(require('fs').readFileSync(process.argv[1],'utf8')); console.log('valid')" /path/to/crm-platform/apps/web/src/features/money/contract/mutaba3a-openapi.json
```

Three traps, all hit on 2026-10-11:

- **Run it from `server/`.** The repository root has no `openapi:json`
  script, and npm answers `Missing script: "openapi:json"`.
- **The shell empties the target before npm starts.** A failed run leaves
  Malafat's file at 0 bytes. Re-run correctly before committing anything in
  Malafat.
- **Keep `-s`.** Without it npm writes its `> @mutaba3a/api … openapi:json`
  banner to stdout, so the file starts with two lines that aren't JSON and
  Malafat's contract test fails to parse it. The `node -e` line above catches
  this.

Then, in Malafat, run the Money contract test and commit the file in the next
web release.

Sessions (MUT-38) added the audit actor `USER` (ADR-037 decision 9). Add
`"USER"` to the `actorType` union in Malafat's
`apps/web/src/features/money/domain/types.ts`. Malafat's client does no
runtime validation and its history view only tests `actorType === "SYSTEM"`, so
a `USER` row cannot break a release that lacks it (checked 2026-10-11). That is
why the 2026-10-11 deploy could go out before this refresh.

### 4b. Give a person access to the hosted portal (MUT-37)

The service reads `SESSION_TOKEN_PEPPER` from the Secret Manager secret
`mutaba3a-api-session-pepper`, which Terraform generates and mounts (MUT-38).
The first `./scripts/deploy.sh` after this change creates it; nothing to do by
hand.

Portal users are operator-issued exactly like keys (ADR-037, TD-018): there is
no signup, invite or "forgot password" route in any environment. Since MUT-235
(ADR-088) the operator never handles a password: `provision:user` prints a
one-time **setup link** **once** (72 hours; `--valid-hours 1–720`). Deliver it
like a key secret. The person sets their own password through it on the portal's
`/setup` page (MUT-236) and then signs in on the portal or the app.

```bash
npm run provision:user -- --url "$URL" --email nour@firm.ps --name "Nour Haddad" \
  --organization-id <uuid> --locale ar
```

Every user is also created with exactly one personal profile (MUT-120). With no
firm, pass `--currency` and `--timezone` instead of `--organization-id`; with a
firm they default to the firm's. A personal profile is never shared, issued an
API key or bound to Malafat (409 `CONFLICT`, `reason: PERSONAL_PROFILE`).

A person in two firms gets a second membership:
`npm run grant:user -- --url "$URL" --email nour@firm.ps --organization-id <uuid>`.
Every account change is audited as `ADMIN` on each organization the person belongs
to, their personal profile included (`user.created`, `membership.granted`,
`membership.revoked`, `user.setup_link_issued`, `user.disabled`, `user.enabled`; the
personal profile also gets `organization.created`). When the person sets their
password through a link, `user.password_set` is audited as `USER`. Events from before
MUT-235 keep the old action `user.password_reset`.

As of MUT-45, the portal is live at the service's own URL (`$URL/`) — a
provisioned person can sign in there directly; `POST /v1/sessions` and
`GET /v1/me` remain available for API-level checks (README "Sessions").

### 4c. Cookies, CORS and CSP (MUT-45) — what is set and why

The portal and the API are **one origin**: the same Cloud Run service serves
both (`src/app.ts`, hosted-portal.md §9), so there is nothing to configure for
cookies or CORS beyond what MUT-38 already built:

- **Cookie**: `__Host-mut_session`, `Secure`, `HttpOnly`, `SameSite=Strict`.
  `__Host-` requires same-origin-only, HTTPS-only delivery — exactly what a
  single-service deployment gives for free (ADR-037 decision 3).
- **CORS**: none. A cross-origin page cannot read the session cookie or call
  `/v1/*` with it; there is no `Access-Control-Allow-Origin` to misconfigure,
  because there is no second origin to allow.
- **Same-origin check for non-GET session requests**: `PORTAL_ORIGIN` is
  intentionally **unset** in production. `isSameOriginRequest()`
  (`src/auth/sessions.ts`) then compares the request's `Origin` header against
  the URL it actually arrived on, which is correct and sufficient as long as
  nothing in front of Cloud Run changes the apparent origin — true today,
  since there is no custom domain (see the note at the end of §5). Setting
  `PORTAL_ORIGIN` only becomes necessary if a reverse proxy or load balancer is
  ever put in front of the service with a different public hostname.
- **CSP**: `default-src 'self'; connect-src 'self' https://storage.googleapis.com;
  img-src 'self' data:; frame-ancestors 'none'; form-action 'self'` on every
  response. `'self'` everywhere else is possible precisely because the portal
  and the API share an origin; `frame-ancestors 'none'` blocks the portal from
  being framed anywhere; `form-action 'self'` and no `script-src` relaxations
  keep the policy as tight as the app allows without inline scripts or
  third-party calls. The one addition to the design brief's draft policy is
  `https://storage.googleapis.com` in `connect-src`: receipt uploads (MUT-44)
  `fetch()` a `PUT` directly to a GCS v4 signed URL — `storage.googleapis.com`
  is the library's default, path-styled host (`@google-cloud/storage`'s
  `PATH_STYLED_HOST`, `virtualHostedStyle` not set) — and `connect-src` governs
  that call. Receipt *downloads* need no entry here: `downloadNavigator.open()`
  is a top-level navigation, which `connect-src` does not restrict.

### 4d. App association files (MUT-111) — what is set and why

iOS only trusts the portal's saved passwords and opens portal links in the app
once the domain declares it via `GET /.well-known/apple-app-site-association`;
Android needs the same declaration via `GET /.well-known/assetlinks.json`.
Both are served by the API itself (`src/routes/well-known.ts`), generated from
config so a domain move (MUT-112) changes no code.

- **Config**: `apple_team_id`, `apple_bundle_id`, `android_package_name` and
  `android_sha256_fingerprints` (Terraform variables, `production.tfvars`) —
  all four or none; a `terraform plan` precondition and `config.ts`'s own
  boot-time check both refuse a partial set. Empty (the default) disables both
  routes entirely — same "absent dependency" shape as `PORTAL_DIST_DIR` and
  `ATTACHMENTS_BUCKET`.
- **Adding a fingerprint**: `android_sha256_fingerprints` is a comma-separated
  list (the debug and upload-key fingerprints at minimum, MUT-114; the Play
  App Signing fingerprint joins later, in the Android epic). Edit the value in
  `production.tfvars`, `terraform apply`, done — no code change, no redeploy
  of the image itself (only the Cloud Run revision's env vars change).
- **Moving domains**: MUT-112's job, not this file's. When it lands, update
  this section with whatever changes (if anything) in how these two routes
  are reached — the `appID`/`package_name` values themselves don't change
  just because the hostname did.
- **Apple's CDN caches the AASA for up to about 24 hours.** A fingerprint or
  path-list change deployed just now will not necessarily be visible to a
  freshly-installed iOS app immediately — don't assume a redeploy is broken
  just because Apple's side hasn't refreshed yet.
- **Verifying it actually works is a manual, post-deploy step** — no test in
  this repo's suite calls Apple or Google's live infrastructure. After a
  deploy that touches these routes, run the live `run.app` URL through:
  - Apple's AASA validator (e.g. `https://search.developer.apple.com/appsearch-validation-tool/`)
  - Google's Digital Asset Links API tester
    (`https://developers.google.com/digital-asset-links/tools/generator`)

  Both must pass before MUT-113 (iOS) or MUT-114 (Android) can be verified
  end to end.

## 5. Wire Malafat to it

In the Malafat repository (`web/crm-platform`), the release contract mounts
`MUTABA3A_API_URL` from a secret. Create it **before** the next web release or
`pnpm release` fails at `gcloud run deploy` (loudly; the old revision keeps serving):

```bash
printf %s "$URL" | gcloud secrets create malafat-web-mutaba3a-api-url \
  --project=malafat-production --data-file=- \
  --replication-policy=user-managed --locations=me-west1
```

Then release web as usual (`pnpm release`), run the tenant migration step
already listed in `scripts/release-steps.ts` (`pnpm db:update_tenants --with-proxy`,
creates `money_integrations`), and in the firm's Malafat as a Partner:
**Settings › Money & Mutaba3a › Connect**, paste the key. The page shows the
organization name, masked key and scopes, and "Test connection" calls
`GET /v1/integration` round-trip.

Optional, deliberately deferred past MUT-45: put `api.mutaba3a.app` in front of
the run.app URL. Cloud Run domain mappings are not offered in `me-west1`, so
this would be a Cloudflare proxied CNAME (the same approach as
`malafat-router`) or an external HTTPS load balancer — either one adds a hop
that changes the origin the browser sees from the one Cloud Run sees, which is
exactly what `PORTAL_ORIGIN` and `TRUSTED_PROXY_HOPS` exist to handle (§4c).
MUT-45 intentionally shipped without it: ADR-037 decision 10 only requires the
portal and the API to share an origin, which the bare run.app URL already
does, at zero extra cost or infrastructure. The run.app URL is stable for the
life of the service; add a custom domain as its own follow-up ticket if a
branded URL becomes a real requirement, not before.

## 6. Day-2 operations

| Task | Command |
|---|---|
| Roll a new commit | `./scripts/deploy.sh` (from `main`) |

### Open: production probably has the original M7 enum (MUT-59, fix ready)

M8 edited the M7 migration in place (D20). `acb1144` created
`FeeProposalStatus` as `('PROPOSED', 'CLIENT_APPROVED', 'AGREED', 'CONVERTED', 'WITHDRAWN')`
and the columns `agreedOn` and `agreedNote`. `main` now creates
`('PROPOSED', 'APPROVED', 'WITHDRAWN')` without them.

Revision `00003` rolled `acb1144`, and `deploy.sh` migrates before it rolls, so
production recorded the original M7. `prisma migrate deploy` never re-runs a
recorded migration. The database therefore still has the old enum while the
service writes `APPROVED`.

What breaks:

- **Approving a fee proposal** fails with a Postgres enum error, which
  reaches Partners as a 500. Malafat `web@2.2.4` offers the button.
- **Reading a proposal in a removed status** fails too.

**Until the fix is deployed, nobody approves a proposal.**

**The fix** is the migration `20261011120000_mut59_fee_proposal_enum_repair`
(MUT-59). It ships with the next `./scripts/deploy.sh` from `main`, in step 4,
before the service rolls. It runs as one statement, so it either does all of
the following or nothing:

- **Refuses** if a `CONVERTED` proposal has no agreement, or if a project would
  be left with two open proposals. The error names the rows.
- **Audits first:** every touched row gets a `SYSTEM` audit event
  `fee_proposal.repaired` holding its previous values. That covers status,
  approval date and note, agreed amount, `agreedOn` and `agreedNote`.
- **Maps the statuses:**
  - `CONVERTED` → `APPROVED`, with the approval date and amount taken from
    M7's fields or else the agreement;
  - `CLIENT_APPROVED` and `AGREED` → `PROPOSED`, i.e. still open, and the
    Partner approves them again in M8, which creates the agreement.
- **Reshapes the schema:** recreates the enum with three values and drops
  `agreedOn` and `agreedNote`.

On a database that already has M8's shape it does nothing.

If step 4 stops with `MUT-59 repair refused: …`:

1. The service was not rolled, and nothing was changed.
2. Fix the named rows in `npm run db:psql`. For example, withdraw a
   `CONVERTED` proposal that has no agreement:
   `UPDATE fee_proposals SET status = 'WITHDRAWN', "withdrawnReason" = '…' WHERE id = '…'`.
3. Mark the migration rolled back:
   1. start the proxy with `TF_STATE_BUCKET=<bucket> npm run db:proxy`, which
      prints the local database URL and waits;
   2. in another shell, run
      `DATABASE_URL=<that URL> npx prisma migrate resolve --rolled-back 20261011120000_mut59_fee_proposal_enum_repair`.
4. Re-run `./scripts/deploy.sh`.
